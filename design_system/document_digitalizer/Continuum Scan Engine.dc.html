Five new axes, and nothing replaced. Continuum's existing tokens already cover surfaces, ink, radii, type and the traffic-light hues — what the scan flow adds is everything that only makes sense when chrome sits on a live camera feed, plus the two physical constraints (safe area, touch floor) a full-bleed screen introduces.

The one decision worth arguing with You asked for the scan flow to follow the user's theme, and it does — except for the four --scan-* tokens, which are the same in both. The chrome around the viewfinder is themed; what floats on the feed is not. A camera frame is not a themed surface: its luminance is unknown and changes every frame, so a light-theme scrim would be unreadable over a dark kitchen and a dark-theme one unreadable over a white page. Switch the theme toggle above while on the Capture tab to see how far that gets you. They are not new colours, though. app.css already has --plate for text that must sit on an unknown ground — chart labels over waterfall ribbons — and these are its dark values held constant. Same problem, same solution, one theme rule apart.

--motion-snap90ms · inherited, button press --motion-capture700ms · the collapse --motion-hold1500ms · the stability ring --motion-settle220ms · sheets, mode swaps --ease-outcubic-bezier(0.2, 0, 0.2, 1)
The product has exactly one transition today — background-color 90ms ease-out on a pressed button — and that easing is the seed the whole set inherits. Duration does not transfer, though: 90ms is right for a 1px tint in place and wrong for travel across a screen, where it falls below the threshold at which the eye reads movement at all. The collapse ran at 90ms and landed as a jump cut rather than a snap, so it has its own token.
Not a token — thumb reach There was a --thumb-zone: 34% here and it has been removed. Thumb reach is a placement rule, not a value any declaration consumes: nothing a one-handed user must reach mid-capture may sit above the bottom third, and the way to honour that is to position the control deck from the bottom edge — which the capture screen does. A token that only ever appeared in a comment is spec pretending to be code.

One design, every upload point — as you asked. UploadDropzone.svelte already exists and already has idle, dragging and busy; it is used in two of the twelve sites. This extends it rather than replacing it, and the extension is one button.

the region/button tension Three affordances, but only two things that look pressable. The dashed region carries click-and-drop together — one dashed rule has meant “a file goes here” for twenty years, and clicking a drop target is the behaviour everyone already tries. Only the camera is drawn as a button, because it is the one affordance nothing about a dashed rectangle suggests.
one design, twelve sites The camera button appears when accept admits an image — a prop the component is already given at every call site. So it is genuinely one component with one design: the Settings JSON restore and the .xlsx broker report simply never draw a button for a thing they cannot use.
nested pressables The camera button sits inside a clickable region, so its handler stops propagation — otherwise tapping it also opens the file browser behind it. The existing component's role="button" and Enter/Space handling stay; the camera is a real <button> and lands next in tab order.

Auto-capture, as you specified Stable fires on its own, and any touch anywhere cancels it — not just a touch on a control. The ring fills rather than counting down: a number invites you to wait for it, a filling ring invites you to keep still, which is the thing that actually helps. The fill runs the length of the whole wait — --motion-hold, 1500ms. It used to complete in 220ms and then sit full, which made the shutter look like it fired for its own reasons rather than at the end of a countdown you were watching. Under prefers-reduced-motion the ring arrives full instead of sweeping, so stability never depends on motion alone. The override covers transitions as well as animations — the ring is a transition on stroke-dashoffset, so an animation-only rule would have missed the single motion the brief marks pass/fail. The capture collapse goes with it, which is the point of the setting.
Steppy at 8–10 fps, on purpose The outline is a plain polygon with no per-frame smoothing, and nothing about it improves at 60 fps. What is transitioned is stroke-width between states, which changes on a state boundary rather than every frame — so the appeal survives a slow detector.
no layout shift The guidance chip is centred with a fixed min-height, so “Move closer to the page” and “Too dark — try more light” occupy the same band and nothing below them moves. Step through the reject states above and watch the shutter stay put.

No corner handles — you decide whether the shot is good and replace it if not, before anything is processed. That removes the loupe, the offset crosshair and the edge-of-frame grab problem entirely, and it makes this screen a two-answer question rather than an editor.

Two answers, not an editor Keep is primary and Replace is secondary, because the shot is usually fine and the flow should not make you confirm that carefully. Replace goes straight back to the camera with this page still in the stack — nothing is lost by trying again, which is what makes skipping corner editing safe.
The mode-switch gap Tapping a mode re-processes, so the tap lands instantly and the page catches up under a scrim that names what it is doing. The note under the switcher has a fixed height so the deck does not jump as the wording changes — and Keep stays live throughout, since the mode can be changed again later.
Why B&W is the default Household paper is text on white, and B&W is where OCR reads best and the file is smallest. Colour is the exception you reach for when the page has a stamp, a signature or a chart worth keeping — so it is the last option, not the first.

Mixed orientations Every tile is the same 3:4 box and the page sits inside it at its own aspect ratio. A landscape page therefore cannot make its row taller than the row beside it, and the grid stays a grid — which is the thing that breaks when thumbnails size themselves to their content.
Five photographs, one document The pages are never separate files in Continuum, so nothing here calls them a batch. The screen names the PDF from the first tap, and the wait is called Combining rather than “Uploading page 3 of 5” — which read as five separate uploads of five separate files. The per-page work is real, so the bar still counts pages; what it counts toward is one document, and a tick means the page is cleaned up and written into it.
One PDF makes failure worse, so say so Four pages on a server are not a document. The Failed state therefore says the four are being held rather than filed — claiming they were filed would be a lie the Documents shelf immediately exposes. It still never re-sends what arrived, and never offers to discard.
The button carries through “Upload PDF” → “Combining into one PDF” → “Uploaded”. Cleaning the pages and writing the PDF were two states with two chips and two bars; to the person holding the phone that is one wait making one file, so it is one state named for the file. The name typed above is what the last label opens.
Page order is the document One PDF means the order of the tiles is the order of the pages — getting it wrong is not a display preference, it is a wrong document. So moving a page is a first-class action: ↑ and ↓ both, at the 44px floor, on their own row. They were 30px and up-only before, which meant the first page reached the end by pressing buttons on four other tiles. Dragging is still the gesture; the buttons are what make it reachable by keyboard, by screen reader, and by anyone whose drag does not register. The grip on each page's badge says which part of a tile to pull. Order locks once uploading starts — the pages are already going in that order.
