# v0.3.9 — Schema lock and production cleanup

**Status:** design, awaiting review
**Date:** 2026-08-19
**Supersedes:** nothing. Establishes the baseline all later work builds on.

## Premise

Continuum has no users yet. That fact expires, and it is the only reason this
release can exist in this form: v0.3.9 rebuilds the database from a single
baseline migration with no conversion path, no compatibility shims, and no
deprecation window.

After this release the schema is additive-only. Every decision below is
therefore made against the question "what will this cost in a year", not "what
is cheapest to write this week".

The roadmap the schema is being locked around: more asset and liability types,
budgeting, scoped sharing with people outside the household, and more
integrations.

## Non-goals

- **Multi-tenancy.** One instance serves one household, permanently. Sharing
  with an accountant or a partner is a scoped read token, not a scope column on
  sixty tables.
- **User-defined asset types.** Asset types are typed tables written in code.
  A jsonb attribute bag would reintroduce exactly the class of bug that
  `property_bill.source` was added to fix.
- **Forecasting.** Reserved, not built. Recurring commitments will reuse the
  calendar's RRULE expansion, so that code must not stay calendar-private.
- **Soft deletes**, beyond the calendar tombstones that sync genuinely requires.

# Part 1 — Schema

## 1.1 Migration strategy

The 46 migrations in `drizzle/` are discarded. `drizzle/` ends this release
containing exactly one migration, `0000`, generated from the rebuilt
`schema.ts`.

Three things in the current migration set exist only as SQL and must be carried
forward by hand, because `drizzle-kit generate` cannot see them:

- the `maintain_transfer_pair_legs()` trigger (0027)
- the `person.role` CHECK constraint (0026)
- the partial unique index on `property_bill` where `source = 'meter'` (0030)

`runMigrations()` at boot is unchanged and remains the only supported way to
build the schema. `drizzle-kit push` stays unsupported: it would produce a
database with the tables but none of the triggers.

## 1.2 Identity and audit

Primary keys become `uuid` rather than `text`. Values are UUIDv7, generated in
the application — time-ordered, so index locality does not degrade as history
accumulates.

Exception: rows whose identity is a hash or an external identifier keep `text`
primary keys, because the value is not ours to choose. That is `session`,
`api_token`, `enrollment_token`, `webauthn_challenge`, `credential`,
`broker_operation`, `broker_position`, and `settings`.

`created_at` and `updated_at` live once, on `entity` (below), rather than being
re-declared on every table. Tables outside the entity hierarchy that need them
declare them explicitly as `timestamptz`.

## 1.3 The entity supertype

Ten of the thirteen current link tables are pure fan-out from three connectors:
`tag` (5 tables), `document` (4) and `contact` (4). Every new module multiplies
them.

A single `entity` supertype collapses those ten into three, while keeping a real
foreign key and a working cascade on both ends of every link.

```sql
CREATE TABLE entity (
  id         uuid PRIMARY KEY,
  kind       text NOT NULL,          -- CHECK, generated from TS (see 1.5)
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (id, kind)
);
```

Every linkable record has an `entity` row: `person`, `account`, `transaction`,
`transaction_split`, `property`, `tenancy`, `loan`, `document`, `contact`,
`tag`, `category`, `subject`, and every future asset type.

### Keeping `kind` honest

The `UNIQUE (id, kind)` on `entity` exists so concrete tables can reference the
pair, which makes a mismatched `kind` unrepresentable rather than merely
discouraged:

```sql
CREATE TABLE document (
  id   uuid PRIMARY KEY,
  kind text GENERATED ALWAYS AS ('document') STORED,
  ...
  FOREIGN KEY (id, kind) REFERENCES entity (id, kind) ON DELETE CASCADE
);
```

A `document` row can only ever point at an entity of kind `document`. This is
not defensive decoration: without it, `document_link` and `tag_link` would both
accept an id belonging to a different kind of record, and the resulting bad row
would read as valid.

### Lifecycle

Deleting the `entity` row cascades to the concrete table and to every link.
The reverse direction needs help, or deleting a concrete row would strand its
entity: each concrete table gets an `AFTER DELETE` trigger removing the matching
`entity` row. Both directions are then safe regardless of which table a caller
deletes from.

Inserts go through one `insertEntity(kind)` helper in the data layer, inside the
same transaction as the concrete insert. The foreign key makes skipping it
impossible.

### The three link tables

```sql
CREATE TABLE document_link (
  document_id uuid NOT NULL REFERENCES document(id) ON DELETE CASCADE,
  target_id   uuid NOT NULL REFERENCES entity(id)   ON DELETE CASCADE,
  PRIMARY KEY (document_id, target_id)
);
CREATE INDEX document_link_target_idx ON document_link(target_id);
```

`tag_link` and `contact_link` take the same shape. Three tables rather than one
`entity_link` with a `relation` column, because the three connectors want
different columns within a year — a note on why a contact is attached, a sort
order for filed documents — and a shared table has nowhere to put them.

**Replaced:** `document_person`, `document_property`, `document_account`,
`document_subject`, `document_tag`, `property_tag`, `loan_tag`,
`transaction_tag`, `transaction_split_tag`, `contact_tenancy`,
`contact_property`, `contact_loan`, `contact_account`.

**Kept explicit:** `loan_property`. It carries `share_pct` — it is a domain
relation, not a link.

Adding a module after this costs one concrete table. Tagging, document filing
and contact linking come with it.

## 1.4 Money and currency

**Money storage does not change.** Every money column stays `bigint` holding
minor units, exactly as today. What changes is that the currency's exponent
stops being implicit.

A `currency` reference table carries it, and every currency column gains a
foreign key:

```sql
CREATE TABLE currency (
  code     text PRIMARY KEY,   -- from Intl.supportedValuesOf('currency')
  exponent smallint NOT NULL,  -- from minorDigits(); 0 (JPY) .. 3 (KWD)
  name     text NOT NULL
);
```

The table is **populated from CLDR at boot**, never hand-seeded:
`Intl.supportedValuesOf('currency')` supplies the codes and `minorDigits()` the
exponents, both already used by `src/lib/money.ts`. Refresh is upsert-only, so a
code that disappears from a future runtime cannot orphan rows referencing it.

### What this is and is not for

Correcting the record, because the first draft of this spec had it wrong: **the
zero-decimal currency defect is already fixed in code.** `money.ts` derives the
exponent from CLDR rather than hardcoding `100`; `import/fingerprint.ts` carries
a v3 version bumped precisely because `minorDigits` stopped assuming two; and
`isCurrencyCode()` already validates against the runtime's own currency list.
Every literal `100` remaining in money-adjacent code is a percentage or a unit
conversion, not an exponent.

So this table is **not** the fix for that. Its single job is integrity Postgres
can enforce: `isCurrencyCode()` runs in the application, so a code written by
raw SQL, a migration, or a path that skips validation still lands today. A
foreign key ends that.

Deriving from CLDR rather than seeding ISO 4217 is deliberate. The two disagree
on real currencies — ISO gives HUF two digits, CLDR gives zero — and `money.ts`
already chose CLDR because it matches how the currency is actually written. A
hand-seeded table would be a second source of truth free to drift from the first,
and hardcoded where the project's standing rule is to derive.

`bigint` minor units top out around 9.2 × 10¹⁶ units — nine hundred trillion
euros — which is not a constraint any household reaches.

### Considered and rejected

Recorded so this is not relitigated later.

- **Fixed scale 10⁻⁴ for every currency.** Would make the import conversion
  constant currency-independent, which is genuinely safer. Rejected because it
  rescales every stored value, every fixture and every demo row for a defect
  the lookup table already fixes, and because scale-4 makes unpayable amounts
  (a hundredth of a cent) representable, so every split and FX result needs a
  deliberate rounding step that minor units get for free.
- **Separate `major` / `minor` / `sign` columns.** Rejected: three columns per
  value, non-canonical states, carry handling on every addition, and every
  `ORDER BY` and range filter has to recompute `sign × (major × 10ⁿ + minor)` —
  which is the single integer, so storing that directly is strictly simpler.
- **Floating point with an equality tolerance.** Workable at household scale —
  drift stays far below half a cent — but it is the largest change of the three
  (every `bigint` column and every `BigInt` code path), it costs exact equality
  in a codebase whose import proof, dedup fingerprints and CSV repair are all
  built on it, and it requires epsilon discipline at every comparison site
  permanently. Rejected as more work for a worse result.

Related: `holding.units` widens from `numeric(18,6)`, which is fine for equities
and too coarse the moment a crypto holding lands.

`loan.interest_deductible` is `integer` today and means a boolean. It becomes
one.

## 1.5 Enumerations

Roughly twenty columns are `text` whose valid values exist only in a comment:
`account.bank`, `account.kind`, `loan.kind`, `loan.regime`, `loan.day_count`,
`loan.accrual_style`, `job.state`, `import_file.proof_class`,
`import_file.source_method`, `import_file.ledger_model`,
`transaction.review_state`, `document.shelf`, `document.expiry_verb`,
`category.group_key`, `property.kind`, `property_bill.source`,
`import_profile.source`, `import_profile.origin`, `rule.provenance`,
`transfer_pair.state`, `calendar_account.provider`, `entity.kind`.

Each becomes a CHECK constraint generated from a single TypeScript `const`:

```ts
export const LOAN_REGIME = ['fixed_period', 'fixed_term', 'floating'] as const;
export type LoanRegime = (typeof LOAN_REGIME)[number];
```

The TS union and the SQL constraint derive from the same array, so they cannot
drift. A unit test reads `pg_constraint` and asserts every enum column's CHECK
matches its array exactly.

Postgres `ENUM` types are rejected: values cannot be dropped or reordered
without recreating the type and every column using it, which is precisely
hostile to an additive-only schema. A CHECK is one `DROP CONSTRAINT` /
`ADD CONSTRAINT` pair.

## 1.6 The valued-asset convention

Every valued thing — `property`, `loan`, `account`, `holding`, and every future
vehicle, insurance policy or pension — exposes the same four concepts:

| Concept  | Type                        | Meaning                                   |
| -------- | --------------------------- | ----------------------------------------- |
| owner    | `owner_person_id uuid` null | null = household-owned                    |
| currency | `text` → `currency(code)`   |                                           |
| value    | `bigint`                    | minor units, signed; liabilities negative |
| as of    | `date`                      | when that value was established           |

The column _names_ stay domain-honest — an account has a `balance_minor`, a
loan has an `owed_minor`, and flattening both into `value_minor` would destroy
meaning to serve a convention. What is uniform is that every such table declares
all four, with the locked types and suffixes, and appears in the view.

The view is the contract:

```sql
CREATE VIEW net_worth_component AS
  SELECT id, 'property' AS kind, owner_person_id, currency,  value_minor,   valued_on   FROM property
  UNION ALL
  SELECT id, 'account',          owner_person_id, currency,  balance_minor, balance_on  FROM account
  UNION ALL
  SELECT id, 'loan',             owner_person_id, currency, -owed_minor,    owed_on     FROM loan
  UNION ALL
  SELECT id, 'holding',          NULL,            currency,  value_minor,   valued_on   FROM holding;
```

The sign convention lives in the view — exactly once — rather than in every
caller that has to remember a loan counts negative.

Net-worth code reads the view and never changes again. Adding an asset type is
one table plus one line here, which makes "forgot to include vehicles in net
worth" a structurally impossible bug rather than a vigilance problem.

## 1.7 Jobs and leases

`import_job` and `calendar_account.syncing_since` each invented lease semantics
independently. A third integration would have made three. They collapse into one
table:

```sql
CREATE TABLE job (
  id           uuid PRIMARY KEY,
  kind         text NOT NULL,        -- CHECK: import | calendar_sync | ...
  subject_id   uuid,                 -- what the job is about, kind-dependent
  state        text NOT NULL,        -- CHECK: queued | running | done | failed
  payload      jsonb,
  blob         text,                 -- base64 bytes, cleared on completion
  byte_size    integer NOT NULL DEFAULT 0,
  claimed_at   timestamptz,          -- LEASE, not a lock
  attempts     integer NOT NULL DEFAULT 0,
  result       jsonb,
  error        text,
  queued_at    timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz
);
CREATE INDEX job_claimable_idx ON job(kind, state, queued_at);
```

`claimed_at` stays a lease rather than a lock, for the reason the existing
`import_job` comment gives: the work is CPU-bound or network-bound and can run
for minutes, and no database lock belongs open across that. A stale lease is
taken over after a timeout, so a crashed worker's job is retried rather than
stranded. `attempts` is new — the current design retries indefinitely.

The next integration inherits crash recovery instead of reinventing it.

## 1.8 Snapshots

`portfolio_snapshot` and `net_worth_snapshot` are keyed on `day` alone. A second
broker collides on the primary key and silently overwrites the first.

Both gain a source dimension: `PRIMARY KEY (day, source_id)`, where `source_id`
is the account or broker the figure came from. Household totals become a sum
across sources rather than a single row that happens to be the only one.

`networth_snapshot` is also renamed `net_worth_snapshot`, for consistency with
`portfolio_snapshot` and with every other multi-word table name.

## 1.9 Budgets — reserved shape

Not built in v0.3.9. The shape is fixed now so envelopes are additive later:

```sql
CREATE TABLE budget_line (
  id          uuid PRIMARY KEY,
  category_id uuid REFERENCES category(id) ON DELETE CASCADE,
  period      date NOT NULL,               -- first day of the period
  target_minor bigint NOT NULL,           -- minor units
  carry_in_minor bigint NOT NULL DEFAULT 0,
  currency    text NOT NULL REFERENCES currency(code),
  UNIQUE (category_id, period)
);
```

`carry_in_minor` stays zero until envelope rollover ships, at which point the
feature is a behaviour change rather than a schema change. Actuals stay computed
live from transactions, as every other total in the app already is.

## 1.10 Locked naming conventions

These bind all future work.

| Thing          | Rule                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| Tables         | singular, `snake_case` (`transaction`, never `transactions`)                  |
| Primary key    | `id`, `uuid`, UUIDv7 — unless identity is a hash or external id               |
| Foreign key    | `<referenced_table>_id`                                                       |
| Money          | suffix `_minor`, always `bigint` minor units, always with a currency in scope |
| Currency       | `currency` for a whole row, or `<name>_currency` per column                   |
| Instants       | suffix `_at`, always `timestamptz`                                            |
| Calendar dates | suffix `_on`, always `date`. `_date` is banned                                |
| Booleans       | `boolean`, named as an adjective or participle, no `is_` prefix               |
| Enum columns   | singular noun; constraint named `<table>_<column>_check`                      |
| Indexes        | `<table>_<columns>_idx`                                                       |
| Link tables    | `<connector>_link`, PK on both columns, index on the second                   |

One deliberate exception: `day` on the snapshot and `currency_rate` tables is a
time _dimension key_, not an attribute of the row, and keeps its bare name. The
convention tests below allowlist it explicitly rather than silently.

Renames this forces, among others: `transaction.amount` → `amount_minor` (it is
already minor units, the suffix was just missing); `transaction.booked_at` (a `date`) → `booked_on`;
`start_date`/`end_date` → `starts_on`/`ends_on`; `property.valued_at` →
`valued_on`; `loan.owed_as_of` → `owed_on`; `account.balance_as_of` →
`balance_on`; `holding.as_of` → `valued_at`; `tenancy.renewal_notice_date` →
`renewal_notice_on`; `document.added_on`/`expires_on` already conform;
`document.amount_currency` → `currency`; `networth_snapshot` →
`net_worth_snapshot`.

Three enforcement tests, because a convention nobody checks is a comment:

1. every column matching `%_minor` is `bigint`, and its table reaches a
   currency;
2. every column matching `%_at` is `timestamptz` and every `%_on` is `date`;
3. every foreign key has a covering index.

## 1.11 Integrity gaps to close

**Unindexed foreign keys** — each is a sequential scan that grows with total
history rather than with the row's own share of it:
`transaction.category_id`, `transaction.suggested_category_id`,
`transaction.import_file_id`, `property_bill.property_id`,
`property_bill.document_id`, `tax_statement_line.statement_id`,
`loan_property.property_id`, `loan_event.transaction_id`,
`tax_statement.person_id`, `tenancy.property_id`, and the second column of
every link table.

**Missing foreign keys:** `broker_operation.position_id` references nothing.
`transaction.transfer_pair_id` stays a soft pointer — that one is deliberate,
to avoid an FK cycle, and the `transfer_pair_leg` trigger already enforces what
matters.

**Missing NOT NULLs:** `import_file.currency`, `import_file.proof_class` and
`import_file.source_method` are nullable because they were added after the table
existed. With a baseline rebuild they can be required.

**Unvalidated formats:** `document.period_month` is free `text` holding a
`YYYY-MM` value. It becomes a `date` pinned to the first of the month.

# Part 2 — Backups and secrets

## 2.1 What is wrong today

`dumpDatabase()` discovers tables from `pg_tables` and dumps all of them, with
no allowlist. `destinations.ts` writes the result into mounted Google Drive,
Dropbox, OneDrive or Nextcloud folders.

Two consequences:

1. **`calendar_account.credential` is plaintext** — a Google OAuth refresh token
   or an iCloud app-specific password. A backup ships the Google token to Google
   Drive. There is no encryption at rest anywhere in the codebase.
2. **Restoring resurrects transient state.** `session` rows come back valid, so
   a restore silently un-revokes every session revoked since the backup —
   `auth_generation` does not save you, because that column is restored too.
   Spent `webauthn_challenge` rows come back unspent.

## 2.2 Table classification

Every table declares a backup class in the schema, exhaustively:

```ts
export type BackupClass = 'data' | 'transient' | 'secret';

export const BACKUP_CLASS = {
  transaction:         'data',
  session:             'transient',
  webauthn_challenge:  'transient',
  enrollment_token:    'transient',
  job:                 'transient',
  calendar_account:    'secret',
  ...
} satisfies Record<TableName, BackupClass>;
```

`TableName` is derived from the schema module, so a new table without a class is
a type error rather than a silent inclusion. A unit test compares the keys
against `pg_tables` as a backstop, since that also catches tables created only
in SQL.

- `data` — dumped normally.
- `transient` — never dumped. Work in flight and short-lived auth state.
- `secret` — dumped without its secret columns, so the row's existence and
  settings survive a restore but the credential does not. Reconnecting a
  calendar after a restore is correct behaviour, not a regression.

Two classifications worth stating explicitly because the obvious answer is
wrong:

- **`setup_claim` is `data`, not transient.** Omitting it would leave a restored
  instance with setup unclaimed, so anyone reaching it first could claim
  administrator. That is a hole, not a convenience.
- **`api_token` and `credential` are `data`.** Restoring should leave passkeys
  working and Home Assistant still talking to the API. These are long-lived
  credentials the user manages deliberately, unlike sessions.

## 2.3 Encryption

Encryption is **two independent layers**, and only the second is optional. That
separation is the point: it lets encryption default to off without the default
install being the insecure one.

### Layer 1 — redaction. Always on, not a setting.

Classification from 2.2 applies unconditionally. `transient` tables are never
dumped; `secret` columns are omitted from the dump entirely.

This is what actually fixes the defect that started this work — a plaintext
Google refresh token syncing to Google Drive. It needs no key, has nothing to
lose, and there is no coherent reason a user would want their OAuth token inside
a file synced to a third party. It is therefore not offered as a choice.

With encryption off, a backup contains the household's financial data in plain
SQL and **no credentials of any kind**. Restoring it means reconnecting
calendars, which is correct behaviour.

### Layer 2 — encryption. Optional, default off, toggled in Settings.

When enabled:

- **Secret columns** (`calendar_account.credential`) are encrypted at rest with
  AES-256-GCM, random IV per value, stored as `v<n>:<key_id>:<iv>:<tag>:<ct>`.
- **Backup files** are encrypted with a random data key, written as `.sql.enc`.
- Node's `crypto` only — no external binary, consistent with `dump.ts`
  deliberately avoiding `pg_dump` so backups work in every install.

Only columns can be encrypted, not the database. Encrypting money or date
columns would destroy filtering, sorting and aggregation, so the scope is
credentials and free-text secrets. Whole-database encryption is a disk-level
concern (LUKS, an encrypted volume) and stays outside the app — the docs should
say so rather than implying the toggle provides it.

### Key handling

Envelope encryption, so key loss takes two failures rather than one:

- A random **data key** does the actual encrypting.
- It is wrapped twice: once by a **machine key** on the data volume
  (`/data/keys/master.key`, mode 0600), and once by a **recovery code** shown
  once when the user enables encryption, with a confirmation step.
- Restoring on the same machine needs nothing typed. Restoring on a new machine
  prompts for the recovery code. Losing the volume _and_ the code loses the
  encrypted backups.
- `APP_SECRET` in the environment remains supported as an override for anyone
  managing secrets properly, but is no longer required.

The machine key living beside the data is deliberate, and the trade is worth
stating: it defends completely against the threat named above — the key never
leaves the machine while the backup does — and not at all against theft of the
volume itself. Someone holding the volume already has every transaction.

### Toggling

**Turning on:** generate the data key and recovery code, show the code once,
require confirmation before proceeding. Encrypt secret columns in place. Future
backups are encrypted. Offer, as a checkbox, to re-encrypt existing backups.

**Turning off:** a security downgrade, so it requires re-authentication. Secret
columns are decrypted in place, and future backups are written plaintext (still
redacted — layer 1 does not turn off). Existing encrypted backups are rewritten
as plaintext.

That rewrite is the sharp edge in this feature, because it mutates files in the
user's cloud-sync folder. It is therefore **write-new, verify, then remove old**,
never in-place truncation. A backup that fails verification is left encrypted and
reported, rather than replaced with something unreadable.

**Retired keys are retained, never destroyed** — kept in `/data/keys/` under
their `key_id`. Switching off, then on again, mints a new key; without retention
every backup taken under the old one becomes permanently unreadable. Keys are
removed only when no backup references them.

If encryption is switched off while the key is _already_ lost, existing
encrypted backups cannot be rewritten. They are left untouched and flagged in
the UI as unreadable, rather than silently deleted.

### Backup file header

Every backup carries a short plaintext header — format version, `key_id`,
encrypted yes/no — so a restore can say _which_ key it needs instead of failing
opaquely. The header is readable without any key by design.

### Verify-after-backup

More important than either layer: after every backup the app decrypts (if
needed) and parses the file it just wrote, and records the result on the backup
screen.

Key loss is only one way a backup fails silently. An unverified backup is the
real risk, and this turns "discovered on the day you need it" into "discovered
on day one".

# Part 3 — Code cleanup

## 3.1 Dead code

A sweep for unused exports, orphaned routes, unreachable branches and stale test
fixtures. The v0.3.8 session already removed eight unreachable exports and an
entire portable-profile layer, which suggests the yield here is real.

`src/lib/server/calendar.ts` exists beside `src/lib/server/calendar/`. That is a
symptom worth chasing generally, not just fixing locally.

## 3.2 Module boundaries

`src/lib/server` holds twenty-odd loose `.ts` files beside nine directories.
`cashflow.ts`, `networth.ts`, `salary.ts`, `tax.ts`, `retirement.ts`,
`transactions.ts`, `splits.ts`, `tags.ts`, `rules.ts`, `rule-mutations.ts`,
`contacts.ts` and `overview.ts` all sit at top level while `import/` and
`calendar/` get folders.

Every domain becomes a directory with an `index.ts`. Cross-cutting plumbing —
`policy.ts`, `files.ts`, `status.ts`, `config-file.ts`, `demo.ts` — moves to
`system/`. The rule afterwards: nothing loose in `src/lib/server` except
`db/` and `system/`, so the next feature has an obvious home.

## 3.3 Comment convention

The strong "why" comments already in this codebase are the standard, not the
exception — the `transfer_pair_leg` note explaining why Drizzle cannot recreate
the trigger is a good example of a comment earning its place.

The convention, applied in one pass:

- A comment explains **why**, never **what**. If it restates the code, delete it.
- No hedging. "probably", "for now", "not sure why but", "this might" — a
  comment either states a fact or should not exist. Where the uncertainty is
  real, say what is unknown and what would settle it.
- No commented-out code. Git remembers.
- No stale TODOs. Each becomes an issue or is deleted.
- No template leftovers that were never true for this project.

## 3.4 Licence headers

Every source file gets:

```ts
// SPDX-License-Identifier: PolyForm-Noncommercial-1.0.0
```

272 files in `src/`, none of which have one today. `package.json` has no
`license` field at all; it gains `"license": "PolyForm-Noncommercial-1.0.0"`.

An ESLint rule enforces the header so new files cannot skip it.

# Part 4 — Production hardening

- **Fail fast at boot.** Validate `DATABASE_URL`, `APP_SECRET` and a writable
  `UPLOAD_DIR` at startup with a clear message naming the missing variable.
  Discovering a missing `APP_SECRET` at the first backup attempt — days later,
  in a cron job — is the wrong time.
- **Health endpoint.** `/healthz` reporting database reachability, whether
  migrations are current, and upload-directory writability. Unauthenticated but
  contentless, so it is usable as a container health check.
- **Structured logging.** JSON lines with level and request id, replacing
  `console.log`. Errors carry the request id the user sees.
- **Resource envelope.** Re-confirm the 300 MiB target after the changes. The
  base64 blob in `job` is the one place memory can spike; reading it in chunks
  rather than whole is the mitigation if the target slips.

# Risks

**Encryption defaults to off, so the default install writes plaintext SQL to a
cloud-sync folder.** Acceptable only because layer 1 redaction is unconditional:
that file contains financial data but no credentials. If redaction is ever made
optional, this stops being acceptable.

**Toggling encryption off rewrites files in the user's cloud folder.** The one
destructive operation in the release. Mitigated by write-new-verify-remove-old,
by retaining retired keys, and by leaving unreadable backups alone rather than
replacing them.

**The currency foreign key can reject data that used to import.** Adding FKs to
15 columns means any existing row holding a code CLDR does not list now blocks
the migration. Mitigated by auditing distinct currency values across all money
tables _before_ adding the constraint, and by keeping the refresh upsert-only.

**`parseAmount` in `tabular/determinacy.ts` defaults `minorDigits = 2`.** The
only exponent default left in the import path. Verify every caller passes the
real value; a default is invisible when it is wrong. Add a JPY fixture to the
import corpus so a regression fails a test rather than waiting for a user.

**The entity supertype changes every insert path.** Every linkable record gains
a second write. Mitigated by the foreign key, which makes a skipped `entity` row
an error rather than a silent omission — the failure is loud by construction.

**The rebuild is large and interdependent.** Suggested order: the currency table
and exponent lookup first (small, and it unblocks the import fixtures), then the
entity supertype and links, then enums and constraints, then jobs and backups,
then the non-schema cleanup. The implementation plan settles this properly.

**Demo and seed data are rewritten once**, for the entity supertype and the
renames. Smaller than it would have been, since money values keep their
magnitudes.

# Acceptance criteria

1. `drizzle/` contains exactly one migration.
2. The trigger, CHECK and partial index from migrations 0026/0027/0030 exist in
   the rebuilt schema, with tests proving it.
3. Every enum column has a CHECK matching its TypeScript `const`; a test asserts
   parity by reading `pg_constraint`.
4. Every `%_minor` column is `bigint`; every `%_at` is `timestamptz`; every
   `%_on` is `date`; no column of type `date` or `timestamptz` falls outside
   those suffixes except the allowlisted `day` dimension keys. Tests assert all
   four.
5. Every foreign key has a covering index; a test asserts it from `pg_indexes`.
6. Every table appears in `BACKUP_CLASS`, enforced by both the type and a test.
7. A backup contains no `transient` table and no plaintext credential; a test
   asserts against a populated database.
8. A restore into a fresh instance leaves setup claimed and revoked sessions
   revoked.
9. Every file in `src/` carries an SPDX header; an ESLint rule enforces it.
10. Nothing loose in `src/lib/server` except `db/` and `system/`.
11. The existing suite (1255 unit tests and the E2E suite) passes; `tsc` and
    lint are clean.
