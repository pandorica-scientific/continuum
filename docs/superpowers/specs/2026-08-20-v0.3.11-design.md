# v0.3.11 — Field-report fixes, editable records, and a category taxonomy users own

**Status:** design, awaiting review
**Date:** 2026-08-20
**Follows:** `2026-08-19-v0.3.9-schema-lock-design.md`

## Premise

This release answers a single session of real use: one person, real bank
statements, a real XTB report, an iPad, and a list of everything that broke or
confused. Nothing here is speculative — every item traces to an observation.

Continuum still has no users, so nothing needs a compatibility path from
v0.3.10. That licence is narrower than it sounds. The v0.3.9 schema lock
declared the schema additive-only from that release onward, and this release
honours it: every change below is a new table, a new column, or data. No table
is dropped, no column changes type, and `drizzle/` gains migrations rather than
being rebuilt. "No users" buys freedom in the _data_ — the demo seed, the
category rows, a test database thrown away — not permission to break the lock
one release after setting it.

## Non-goals

- **Multi-address passkeys.** A credential is bound to one relying-party ID, so
  an allowlist would mean enrolling separately per hostname. The fix here is to
  stop advertising passkeys where they cannot work, and to document a single
  HTTPS address that works everywhere.
- **A free-form colour picker for categories.** Every series colour in
  `app.css` carries a hand-tuned light and dark value. An arbitrary hex is
  illegible in one theme or indistinguishable from its neighbour in both.
- **Reworking the transfer matcher.** The pairing machinery is correct and
  already excludes matched pairs from every total. Only the one-sided case is
  missing.
- **Budgeting, forecasting, new asset types.** Reserved for later releases.

# Part 1 — Correctness bugs

## 1.1 XTB import fails on any operation that references a position

**Observed:** uploading an XTB report fails with

```
insert into "broker_operation" (…, "position_id") values (…)
on conflict ("id") do update set "position_id" = $9
params: 1347965304, Withholding tax, PEP.US, …, corr PEP.US USD WHT 15%, 1233431485
```

**Root cause.** `broker_operation.position_id` carries a real foreign key to
`broker_position.id` (`src/lib/server/db/schema/investments.ts:37`). Inside the
ingest transaction, `src/lib/server/invest/ingest.ts` inserts _every operation_
first (line 108), then _every position_ (line 130). The constraint is not
deferrable, so the first operation naming a position that is not already stored
aborts the transaction. The bug is invisible on a first upload whose operations
happen to be position-free, and fires the moment a report carries a dividend,
a withholding tax, or a close.

**Fix.** Two changes, both required:

1. Move the `brokerPosition` loop above the `brokerOperation` loop. Positions
   are self-contained — they reference only `currency` — so nothing depends on
   operations existing first.
2. Reordering alone is insufficient. A report may reference a position it does
   not itself contain: a correction posted in July against a position opened
   and closed in an earlier reporting window, where the user only ever uploads
   recent reports. Build the set of position ids the report carries, union it
   with the ids already stored, and write `positionId: null` for any operation
   naming a position outside that set. The operation is still recorded with its
   full amount and comment; only the link to a holding interval is absent,
   which is exactly true.

The `onConflictDoUpdate` that backfills `positionId` on re-upload must use the
same guard, otherwise a later report re-linking an old operation reintroduces
the failure.

**Tests.** Unit tests over `ingest`, against a report where (a) an operation
precedes its position in the file, (b) an operation names a position absent
from the report entirely, (c) a re-upload backfills a `positionId` that has
since become resolvable. Each asserts the transaction commits and the operation
row exists with the expected `positionId`.

## 1.2 The same import error is rendered twice

**Observed:** the failure appears in a bordered box near the top _and_ again
under the "drop the XTB account statement here…" dropzone.

**Fix.** Keep the boxed rendering, add a dismiss `✕` that clears the error
state. Remove the second rendering beneath the dropzone. The investments page
is the only screen with this duplication; the pattern is not repeated
elsewhere.

## 1.3 The Accounts tab stops responding after a statement import

**Observed:** after importing a statement containing transactions, clicking
Accounts in the sidebar does nothing at all — no navigation, no error screen,
no visible change.

**This is the one item in the release with no diagnosed root cause, and it must
not be guessed at.** The absence of an error page is itself evidence: a
throwing `load` renders SvelteKit's error boundary, so the failure is not a
plain exception. That leaves a hanging promise in `load`, an unhandled
rejection stalling the client router, or a click handler that never fires.

The `load` in `src/routes/(app)/accounts/+page.server.ts` does four things that
only become reachable once transactions exist: FX conversion per account via
`loadRateTable()`, a donut over cash accounts, a `transfer_pair` query, and a
join fetching both legs of each pair.

**Approach.** Reproduce before fixing. Start the app, import a statement with
transactions, click Accounts, and capture the browser console, the network
request for the navigation, and the server log together. Only then write the
failing test and the fix. If reproduction fails, the item stays open rather
than being closed by a speculative change.

## 1.4 "File" on a transaction appears to do nothing

**Observed:** pressing File on a transaction row produces no visible change.
The reporter also read the button as "attach a file", which it is not.

**Root cause.** Two defects behind one symptom, at
`src/routes/(app)/transactions/+page.svelte:170`.

_No feedback on failure._ For an unfiled row, the placeholder option is
`disabled selected`, so the form posts an empty `categoryId`.
`fileTransaction` rejects it and the action returns `fail(…)` with a message —
which has nowhere to render beside that row. For an already-filed row, the
stored category is `selected`, so pressing File resubmits the same value and
nothing changes. Either path is silence.

_The word "file" is overloaded._ Here it means "file under a category". The
adjacent Documents feature means "a file". A button labelled `File` next to a
dropdown reads as an upload control to anyone who has not read the source.

**Fix.** Rename the button to `Save` and the placeholder to `Choose a
category…`. Surface the action's failure message inline against the row that
produced it, using the existing `ActionError` component. Disable the button
until a category is chosen, so the empty-post path cannot be reached at all.
Confirm a successful save visibly — the row's state pill changes from
`needs review` to `filed by hand`, which already happens but is easy to miss;
make that transition legible.

The import review screen carries the same control under the label `File it`
(`src/routes/(app)/import/+page.svelte:344`). It is renamed and given the same
disabled-until-chosen and inline-error treatment, because leaving the two
screens disagreeing would trade one confusion for another.

Actual document attachment is Part 6.1.

## 1.5 "This month" is empty because the month has not been imported

**Observed:** _Where the money goes_ shows nothing, because statements arrive
after the month ends and the current month has no data yet. Affects both the
Overview panel and the Money screen.

**Fix.** Neither screen should ask for the calendar month. Both resolve to the
newest month that actually holds transactions, and name that month in the
panel header so the period is never ambiguous. A household mid-way through
importing sees "July 2026" and understands why, rather than seeing an empty
chart and assuming the app is broken.

The resolution belongs in one server-side helper — `latestMonthWithData()` —
shared by the Overview panel and the Money screen, not duplicated. An instance
with no transactions at all returns null and both screens show their existing
empty state.

**Which date decides the month.** `value_on` when the statement printed one,
falling back to `booked_on` — the same preference the cashflow aggregation
already applies, so the month this helper names is the month those figures were
actually grouped into. Using `booked_on` here while cashflow uses `value_on`
would put a month-boundary transaction in one screen's total and not the
other's.

Transfer legs are excluded when deciding the month, on the same footing as they
are excluded from the figures. A month containing nothing but transfers between
your own accounts has no spending to show, and selecting it would reproduce the
empty chart this section exists to fix.

## 1.6 "Saved each month" has no Y scale and no hover readout

**Fix.** Add a labelled Y axis with ticks, and a hover readout giving the month
and the exact amount. Match the axis and tooltip treatment already used by the
other charts rather than inventing a second style; where no shared primitive
exists, extract one so the third chart does not produce a third style.

## 1.7 "Every month on record" always labels years

**Observed:** the X axis shows years even when the history is a few months
long, which wastes the axis.

**Fix.** Choose the tick unit from the span of the data. Below 24 months, label
months. At or above 24 months, label years. The threshold is a named constant
with the reasoning beside it, since it is a presentation judgement and not a
derived fact.

## 1.8 "Add a passkey" stays on screen after a passkey is added

**Observed:** registering a passkey succeeds and the passkey appears in the
list, but the add button remains.

**Not a defect.** Reading the code disproved the obvious explanation. The
button is not conditional on the passkey count — `PeopleSettings.svelte:167`
renders it whenever passkeys are available at all — and the ceremony already
calls `invalidateAll()` on success (line 66), so the list refreshing while the
button stays is the design working as written. It is deliberate: passkeys are
per-device, and a household with a laptop and an iPad needs to register two.

**What is actually wrong** is that the button gives no sign it did anything.
Nothing on screen distinguishes "your passkey was added, and you may add
another" from "that failed, try again" — so the unchanged button reads as
failure, which is how it was reported.

**Fix.** Say what the button is for. When the person has at least one passkey
registered, it reads `➕ Add another passkey`; with none, `🔑 Add a passkey`.
Confirm the registration briefly beside the newly added row. No change to the
invalidation, which is already correct.

This item is a label and a confirmation, not a bug fix, and the plan sizes it
accordingly.

## 1.9 The Czech tax-deductibility line leaves Loans

**Observed:** _"Interest is tax deductible (owner-occupied mortgage)"_ is Czech
tax law stated as a general fact, on a screen with no jurisdiction concept.

**Fix.** Remove it. Tax statements already carry the real figures, sourced from
documents rather than asserted by the app.

# Part 2 — Interface consistency

## 2.1 Buttons give no sign they were pressed

**Observed:** _"pressing buttons is hard to see, there should be a change of
colour, animation or something to indicate that the button was pressed."_

**Fix.** A single `:active` treatment on the shared `.btn` class in `app.css` —
a background shift and a small transform, with a transition short enough to
register on a fast click. This is one rule in one place; the value is that
every button in the product inherits it. Respect
`prefers-reduced-motion` by dropping the transform and keeping the colour
change.

Forms that submit and re-render need the same care: a submitting button shows a
pending state rather than looking inert while the server works.

## 2.2 Fonts are not standardised

**Observed:** _"not everything has the same font, for example in settings some
elements have different fonts."_

**Fix.** Audit every `font-family`, `font-size` and `font-weight` declaration in
component styles. The product ships two families — Inter Variable for text and
Source Code Pro for figures — and any third is a mistake. Sizes and weights
become tokens in `app.css`; component styles reference the tokens. Settings is
the worst offender and is done first, then the remaining screens.

This is deliberately scoped as an audit with a checklist, not a redesign.

## 2.3 Fields that do not explain themselves

**Observed:** the property screen has a `tag…` box with no explanation, and on
a narrow screen the account-number field's helper text is cut off before it can
be read.

**Fix.** Use the existing `InfoHint` component, which already solves bubble
placement near a viewport edge:

- **Account number** — "The account numbers this account is known by, as your
  statements print them. Continuum uses these to recognise transfers between
  your own accounts so they are not counted as spending." That is what
  `account.numbers` genuinely does; the transfer matcher reads it.
- **Property tags** — a short line on what a tag is and where tagged records
  resurface.

Both hints sit as an ⓘ at the right-hand end of the field's label row, so they
survive narrow widths where inline helper text does not.

## 2.4 Narrow-screen truncation

The account-number report was found on a small screen. Sweep the forms —
accounts, property, loans, settings — for labels and placeholders that clip,
and let them wrap rather than truncate. No responsive redesign; this is a
defect sweep with a phone-width viewport.

# Part 3 — Records that can be edited

A theme runs through the reports: records can be created but not corrected. A
mortgage that forgot a property, an estimated value that moved, a lease with no
end date — each currently means starting over.

## 3.1 Property values gain inline editing

Estimated value, mortgage owed and the other figures on the property screen get
a pencil control at the right of each row, opening an inline edit that saves
that field alone. Values that are _derived_ — anything computed from loans or
transactions — do not get a pencil; they get the ⓘ treatment from 2.3 naming
where the number comes from. Making a derived figure look editable is worse
than leaving it alone.

## 3.2 A lease may have no end date

**Observed:** _"lease ends may not have an end date (a simple checkbox)."_

The tenancy form gets an _open-ended_ checkbox that clears and disables the end
date. Everything reading a tenancy must treat a null end as "still running"
rather than as missing data — the occupancy calculations, the calendar, and
any renewal reminder. Audit each reader; a null end date silently coerced to a
date is a wrong rent figure, not a cosmetic bug.

## 3.3 Adding a tenant creates or links a contact

**Observed:** adding a tenant did not add them to Contacts.

The tenancy form searches existing contacts as the name is typed. A match can
be linked; no match creates a contact and links it. The check happens before
creation, as reported, so a returning tenant does not become a second contact.
`contact_link` already targets any entity and `tenancy` is a registered entity
kind, so this is form and query work with no schema change.

Matching is on normalised name, offered as a suggestion for the user to
confirm. Automatic merging on a fuzzy match is not built — two people can share
a name, and silently merging them corrupts a record that is hard to untangle.

## 3.4 Loans can be edited

**Observed:** _"should also allow for edits, for example if [I] forgot to add
another property into a mortgage."_

The loan screen gains editing of the loan's own fields and of its property
links, through the existing `loan_property` join. Guarded by the constraint
recorded in the project's memory and honoured here: **editing a loan must never
delete fixation periods that follow the edited point.** The fixation history is
the loan's evidence. Any edit path that could truncate it is wrong, and the
tests for this section assert non-destruction explicitly rather than merely
asserting the edit succeeded.

## 3.5 Adding a bank that is not on the list

**Observed:** choosing _Other_ when creating an account should open a dialog to
name a new bank, and that bank should then persist in the list.

The bank list is currently a hardcoded `<option>` set in the accounts page plus
a `BANK_EMOJI` map in its loader. Banks become a small table — key, label,
emoji — seeded with the five that exist today. Choosing _Other_ opens a modal
that captures a name and an emoji, writes the row, and selects it.

This removes a hardcoded list in favour of data, which is the standing
principle for this codebase: constants are for format facts and arithmetic, not
for things a household will legitimately extend.

## 3.6 A mortgage payment can be assigned to a property — CLOSED, not built

**Decided 2026-08-20: the loan's property shares already cover this.**

The reported need was per-flat costs for one mortgage across two properties.
Tracing it showed the property screen never reads the transaction ledger:
`finance.ts:186` allocates owed, principal and payment across flats by their
`loan_property` share, bills are `property_bill` rows, and cash flow is
`rent − bills − payment share`. The screen models the arrangement, not the
ledger, and does so consistently.

Section 3.4 made those shares editable. Setting 60/40 across the two flats
therefore makes every per-property figure correct, which is the whole of what
was asked for.

Attributing an individual imported payment to a flat would have been a
different thing: introducing ledger-driven figures into an arrangement-driven
screen, moving the equity and cash-flow numbers from what was agreed to what
was paid. Adding the column without that change would have stored data nothing
reads. Neither was wanted, so neither was built.

# Part 4 — A category taxonomy the household owns

## 4.1 The problem

`src/lib/categories.ts` hardcodes seven groups — each carrying a label, a chart
colour and a waterfall position — and seventeen leaves. Leaves are already
database rows (`category`), seeded from that constant and editable in
principle. Groups are not: they exist only in code.

The reports against it are all consequences of that: internet and phone share
one leaf and cannot be told apart; there is no pharmacy; there is no
reimbursement; and there is no way to add any of them without an edit and a
deploy.

## 4.2 Groups become data

A `category_group` table with:

| column        | meaning                                        |
| ------------- | ---------------------------------------------- |
| `key`         | stable identifier, primary key                 |
| `label`       | display name                                   |
| `color_token` | name of a CSS custom property, e.g. `--indigo` |
| `role`        | `income` \| `expense` \| `savings`             |
| `sort`        | position within its role                       |

`role` is the column that cannot be omitted. The waterfall is not a flat
ordering — income opens it, expense groups are its stages, and savings closes
it. A group with a colour and a sort order but no role has no defined place in
the chart, and "income" is not merely "the group that happens to sort first".

`category.group_key` becomes a real foreign key to this table. It is `text`
today with no constraint, so this is an added constraint on existing data, not
a type change.

## 4.3 The seeded taxonomy

The seven existing groups keep their keys, colours and order. Two are added:

- **Health & care**, `--indigo` (the one unused series token), role `expense`,
  placed after Bills. Pharmacy, doctor and dentist currently fall into
  "Everything else", which hides a category of spending that is both
  significant and tax-relevant in this jurisdiction.
- **Subscriptions**, role `expense`, placed after Bills. Takes the first token
  from the reserve palette described in 4.4, since `--indigo` was the last free
  one in the existing set.

Leaves added and changed:

- `internet-phone` splits into `internet` and `phone`.
- `pharmacy` and `doctor-dentist` under Health & care.
- `subscriptions` under Subscriptions.
- `reimbursements` under Income — money returning to the household is income at
  the ledger level, whatever prompted it.

Because there are no users, the split of `internet-phone` is a data change with
no reassignment problem: nothing stored points at the old leaf on any instance
that matters — not a transaction, not a split line, and not a learned rule,
each of which carries a `category_id`. A comment records that this would have
needed a reassignment step for all three had it come later.

## 4.4 Users create their own groups and leaves

Both are created from a modal, reachable from the import review screen — where
the need is felt — and from a settings screen that lists the whole taxonomy.

Creating a **leaf** asks for a name and a group. Creating a **group** asks for a
name, a role, and a colour chosen from the curated palette. The palette is
presented as swatches; a group takes an unused token by default so that the
common case needs no colour decision at all.

Colour is a choice from tokens, never a free hex, for the reason given in the
non-goals.

**The reserve palette.** The eight series colours in `app.css` today exist to
serve seven seeded groups; a household that adds groups exhausts them
immediately. Five to ten further tokens are therefore defined up front and held
in reserve, so adding a group in a year's time is a choice from swatches rather
than a colour-design exercise nobody wants to do at that moment.

Each reserve token is a full citizen of the design system and carries both a
light and a dark value, like every existing series colour. Three constraints
bind the set:

- Distinguishable from all eight existing series colours and from each other,
  in both themes — these appear side by side in a donut and stacked in a
  waterfall.
- Distinguishable to the common forms of colour vision deficiency, since the
  chart carries meaning by colour alone in the donut.
- Sufficient contrast against both `--card` backgrounds to be legible as a
  small swatch and as a thin chart segment.

Tokens are named for the colour, not for a use — `--rose`, not
`--subscriptions` — because any group may claim any token.

If the reserve is exhausted too, the honest answer is that the chart has more
series than a person can distinguish, and the modal says so rather than
generating a colour.

**Deletion and renaming.** Renaming is free. Deleting a leaf that transactions
reference must reassign them, not orphan them — the modal asks where they go.
Deleting a group requires it to be empty. Seeded groups and leaves are
deletable like any other; nothing is privileged, because a household that does
not drive should be able to delete Transport.

A role may therefore end up with no groups at all, and that must render rather
than break. The waterfall omits an absent stage; an instance with no `income`
group shows a waterfall that opens at zero. This is the honest depiction of a
taxonomy in that state, and it is preferable to blocking a deletion the user
has a legitimate reason for. The chart code is tested against each role being
empty.

## 4.5 Consumers stop importing the constant

Every consumer of `CATEGORY_GROUPS` moves to reading the table. The constant
survives only as the seed. The waterfall, the Sankey, the donut and the
breakdown strip all derive colour and order from group rows, so a user-created
group renders correctly everywhere without further work.

# Part 5 — Transfers with only one side

## 5.1 What already exists

This deserves stating plainly, because the field report asked for a _category_
called "transfer between own accounts" and that would have been the wrong fix.

Transfers are already a modelled type. `transfer_pair` records a matched pair
with `auto`, `confirmed`, `proposed` and `rejected` states;
`transaction.transfer_pair_id` points back; matched legs are excluded from
cashflow (`cashflow/index.ts:65`), from the overview totals
(`overview/index.ts:375`) and from the briefing. The import screen shows a
"Transfers paired — excluded from income and spending" tile and offers
✓ Own transfer / ✕ Not a transfer on candidate rows.

A category would have been strictly worse: the money would still have been
counted on both sides, and every total would have been quietly wrong.

## 5.2 What is missing

Pairing needs both legs. Money moved to a savings account whose statements are
never imported has one leg only, so nothing matches, and the row sits in the
review queue looking like unexplained spending. This is almost certainly what
prompted "transfer for savings account".

**Fix.** Allow a row to be marked as a transfer to an account that is not
imported. The review queue offers this alongside the existing transfer actions.
The row is excluded from spending on the same footing as a matched pair, and
labelled as one-sided so the distinction survives — a matched pair is verified
by two statements, a one-sided transfer is asserted by a person, and a later
report should not confuse them.

The destination is a household account record, which may exist without any
imported statements. That is already representable.

# Part 6 — Attachments and first-run

## 6.1 A document can be attached to a transaction

The reporter expected the File button to attach a document. The data model
already supports exactly that: `document_link` targets the generic `entity`
table, and `transaction` is a registered entity kind
(`src/lib/enums.ts:55`). No schema work is required.

The transaction row gains an attach control — upload a new document or link an
existing one — and shows what is attached. Documents attached this way appear
in Documents like any other, filed against the transaction.

## 6.2 A first-run guide that writes nothing

**Observed:** _"first time start should have a guide, we can use demo data
embedded in the code… this is per user, so if a new person is added the guide
should be offered to them."_

**Approach: the fixture is rendered, never stored.** The tour draws real
screens from an in-code fixture — a fictional household with accounts,
transactions, a property and a portfolio — without writing a single row.

The alternative, seeding the demo household and removing it later, was
rejected. It reuses the existing `demo.ts` seeder almost unchanged, which is
its whole appeal, but it puts fictional transactions into the same ledger that
holds real money for as long as the tour runs, and a cleanup that fails once
leaves them there permanently. In a product whose entire value is that its
numbers are trustworthy, that trade is not worth the saved effort.

The consequence, stated honestly: tour screens read from the fixture rather
than from the page loaders, so each screen in the tour needs a rendering path
that accepts injected data. That is real work, and it is the price of the
guarantee.

**Per person.** The offer is tracked per person, not per instance. A new
household member is offered the tour on first sign-in even though the instance
is long established. It is dismissible and re-runnable from Settings.

`demo.ts` and `DEMO=1` stay as they are — a separate mechanism for
screenshotting a populated instance. The fixture may share its data shape, but
the tour never invokes the seeder.

# Part 7 — Authentication

## 7.1 The setup password is entered once

**Fix.** Add a confirmation field to `src/routes/setup/+page.svelte` and check
the two match before the account is created. A typo in the only password on a
fresh instance currently locks the owner out of their own instance
immediately.

## 7.2 Passkeys are offered where they cannot work

**Observed:** the passkey button appears on `continuum.local` and on the iPad,
where it fails; it works only on `http://localhost/login`.

**Root cause.** `passkeysAvailable()` in
`src/lib/server/auth/webauthn/origin.ts:49` evaluates the static `ORIGIN`
environment variable, not the origin of the request being served. An instance
reachable at several addresses therefore shows the button at all of them while
only the configured one can verify — `compose.yaml:25` defaults `ORIGIN` to
`http://localhost`, which explains the reported behaviour precisely.

The underlying constraint is real and not a defect: browsers refuse WebAuthn
outside a secure context, and only loopback is exempt. `isSecureOrigin` encodes
this correctly.

**Fix.** Decide availability from the request's own origin. The passkey UI
appears only when the address actually being browsed is secure _and_ matches
the configured origin. Elsewhere, a short line states why it is absent and what
would make it work, rather than an unexplained absence — or worse, the present
button that fails.

**Documentation.** `docs/install.md` gains a section on giving the instance one
HTTPS address that works from every device: Caddy with a local certificate
authority, or Tailscale. This is the actual answer to "passkeys on the iPad",
and no code change substitutes for it.

## 7.3 A passkey is offered first when one exists

Where a person has a registered passkey and the current address supports
passkeys, sign-in leads with the passkey and offers the password as the
secondary path. Nothing is removed; the order changes.

## 7.4 Open mode

**Requested:** the ability to opt out of credentials entirely — _"only an admin
can do it, not a normal user, and then this behaviour is for all users."_

**Shape.** One instance-wide setting, not a per-person flag. When enabled, the
login screen's person picker signs the chosen person straight in with no
credential.

**Rules.**

- Only a person with the `admin` role can enable it.
- **Enabling requires the admin to re-enter their password**, which proves
  intent while a password still exists to prove it with.
- Disabling requires no credential, from any session. The door can always be
  closed, including by someone who walked in through it.
- Passwords are not deleted. Turning open mode off restores normal sign-in with
  every existing credential intact.
- The setting is surfaced with an unambiguous warning, and while it is on, an
  indicator is visible in the application shell — not buried in settings — so
  the state is never a surprise.

**The consequence, recorded rather than mitigated.** With open mode on, anyone
who can reach the URL is any person on the instance, including the admin, and
can read every statement, salary figure, mortgage balance and tax statement,
use the API, and export everything. On a plain-HTTP LAN address that is
everyone on the network. This was raised during design and confirmed as the
intent. It is documented here so the decision is legible later, and the warning
text in the interface says the same thing in one sentence.

**What it does not touch.** Open mode governs interactive sign-in only. The
`/api` authentication boundary, calendar `.ics` tokens and enrolment tokens keep
their own checks. That boundary is load-bearing and is not to be routed around
by this feature.

# Part 8 — Schema changes

Every change is additive, per the v0.3.9 lock.

| change                                        | kind                                      |
| --------------------------------------------- | ----------------------------------------- |
| `category_group` table                        | new table                                 |
| `category.group_key` → FK to `category_group` | added constraint                          |
| `bank` table                                  | new table                                 |
| `account.bank` → FK to `bank`                 | added constraint                          |
| one-sided transfer marker on `transaction`    | new column                                |
| tour-completion marker on `person`            | new column                                |
| open-mode setting                             | existing settings store, no schema change |

Nothing is dropped and no column changes type. The two added foreign keys
constrain columns that are unconstrained text today.

# Part 9 — Testing

- **Unit** — the XTB ordering and missing-position cases; `latestMonthWithData`
  including the empty instance; the axis-unit threshold; category and group
  creation, rename, reassignment on delete, and refusal to delete a non-empty
  group; open-mode enable requiring a password and disable not requiring one.
- **End-to-end** — file a transaction and see the result; add a bank through

  afterwards.
- **Reproduction-gated** — the Accounts hang gets a regression test written
  against the reproduction, not before it.

# Part 10 — Sequencing

This spec is one design covering one release, but it is too large for one
implementation plan. Each part below becomes its own plan, written and executed
in this order, so that a part can ship and be used before the next begins.

1. **Part 1**, bugs, independently shippable. The XTB fix first — it blocks a
   real workflow today.
2. **Part 2**, consistency. Small, broad, low-risk, and improves everything
   built afterwards.
3. **Part 4**, the taxonomy, before Part 3 — the import screen's category modal
   sets the pattern the other modals follow.
4. **Part 3**, editing, and **Part 5**, one-sided transfers.
5. **Part 7**, authentication.
6. **Part 6**, attachments and the tour, last: the tour should show the product
   as this release leaves it.
