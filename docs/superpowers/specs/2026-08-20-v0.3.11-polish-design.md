# v0.3.11 polish — a second field report

**Status:** design, awaiting review
**Date:** 2026-08-20
**Follows:** `2026-08-20-v0.3.11-design.md`
**Branch:** `feat/v0.3.11` · **Version:** unchanged at 0.3.11

## Premise

The first v0.3.11 design answered one session of real use. This answers the
next one, on the build that came out of it: the same household, the same
statements, now on a phone as well as a desktop. Thirty-four observations,
plus two pieces of groundwork the observations argued for.

**Order matters here.** Part 0 lands first because every later part is
CSS-heavy and would otherwise add values it then has to migrate. Part 7 lands
last because it needs Part 3's category picker and Part 4's account ownership.
Parts 1, 2, 5 and 6 are independent of each other.

Every item below was traced to code before it was written down. Where the
cause is proven, it is stated. Where it is not, the item says so rather than
proposing a fix for a guess.

Two of the reported failures were reproduced against the reporter's own files
and are settled facts, not hypotheses:

- The real Revolut export fails its balance proof because three `Savings`
  rows share a statement with 1798 `Current` rows. Removing only those three
  takes the file from **P0, "the running balance does not follow from the
  movements"** to **P3, "the chain closes on all 1798 rows"**.
- The Fio `Pohyby na účtu` export carries no balance column at all, so it is
  P0 by construction and refused by design. That refusal is correct.

## Non-goals

- **Weakening the P0 refusal.** `proof.ts:443` refuses a statement that
  nothing in it can check, even when a person has confirmed the column
  mapping, and the reasoning in that comment holds: confirming a mapping says
  the columns mean what we think, not that the rows under them are all there.
  A file with no balances gets a better refusal, not an exception.
- **Multi-address passkeys.** Unchanged from the previous design: a credential
  is bound to one relying-party ID. Part 2 makes _password_ sign-in work from
  every address; passkeys still work at exactly one.
- **Changing an account's currency after it holds transactions.** The account
  is the currency authority for everything filed against it; stored amounts
  are minor units of that currency. Editing it later would reinterpret every
  row.
- **Deleting import history.** The ✕ controls in Part 3 dismiss rows from a
  view. Nothing they touch removes an `import_file` record, a transaction, or
  a stored statement.
- **A version bump.** This lands on `feat/v0.3.11` as 0.3.11.
- **Restyling anything.** Part 0 gives the existing values names and enforces
  them. It does not change how the product looks: the scales are derived from
  the values already dominant in the code, so a correct migration is invisible
  on screen. Any visible change is a bug in the migration, not a feature of it.

# Part 0 — One vocabulary for shape and spacing

Lands first. Every later part is CSS-heavy and would otherwise add values this
sweep then has to migrate.

## 0.1 What is already standardised, and is not touched

Measured before deciding, because three of the four things this part was
originally scoped to fix turned out to be done already:

- **Colour.** Nine raw literals in the whole of `src`, and most are legitimate:
  three scrim overlays, and two hex values in the `theme-color` meta tag, which
  a browser API requires to be literal. Against roughly sixty tokens.
- **Type.** Nine tokens, collapsed from twenty-two earlier in this release.
- **Buttons.** One global `.btn` in `app.css:356` carrying hover, `:active`,
  `:focus-visible` and `:disabled`, plus `.btn-primary`.

None of these needs work. Saying so here stops a later reader "finishing the
job" on something that was never broken.

## 0.2 What is not standardised

|                 | Distinct values in use                                                            |
| --------------- | --------------------------------------------------------------------------------- |
| `border-radius` | 23                                                                                |
| `gap`           | 12+, with no scale                                                                |
| `padding`       | dozens of near-twins — `9px 14px`, `8px 11px`, `7px 11px`, `9px 11px`, `8px 10px` |
| control height  | no token at all                                                                   |

And the recipe for a form control — six declarations — is copied about fifteen
times. It has **already drifted**: `padding: 8px 11px` everywhere except
`login/+page.svelte`, which says `9px 11px`. Nobody noticed, and nothing would
have.

That is the same class of defect as the payslip row in 1.6, where four controls
in one row measured 36, 36, 34, 42 and 32 pixels tall against
`align-items: end`. The fix there had to invent a form-local
`--payslip-control-h`, because there was no shared height to reach for. The
local token is the symptom, and this part is what lets it be deleted.

## 0.3 Tokens, and how the scale was chosen

The first draft of this section proposed `--space` on `{4,6,8,12,16}` and
`--radius` on `{6,8,12}`. Both were measured against the code before anything
was built, and both were **wrong**:

| Draft scale         | Uses it would have changed visibly |
| ------------------- | ---------------------------------- |
| gap `{4,6,8,12,16}` | **112**                            |
| radius `{6,8,12}`   | **62**                             |

That is not standardisation, it is a restyle of 174 places — the exact thing
§0.2's non-goal forbids. The scale is therefore derived from what the code
actually uses, not from a tidy-looking progression:

```
--radius-xs: 4px     --space-1: 2px      --control-h: 36px
--radius-sm: 6px     --space-2: 4px
--radius-md: 8px     --space-3: 6px
--radius-lg: 10px    --space-4: 8px
--radius-xl: 12px    --space-5: 10px
--radius-2xl: 16px   --space-6: 12px
--radius-pill: 999px --space-7: 14px
                     --space-8: 16px
```

With these, 283 of 363 `gap` uses and 106 of 142 `border-radius` uses are
already exact, and a further 67 and 10 are within a single pixel — a snap no
eye can see. Thirteen gaps and roughly a dozen radii remain, and they are
genuine one-offs rather than drift: the 88px and 148px donut, `50%` circles,
the 999px pills, a handful of large decorative corners.

An eight-step spacing scale is wider than a design system would usually
choose. That is a deliberate concession to an existing codebase: a tighter
scale is only tighter on paper if adopting it means restyling a hundred
screens.

## 0.4 Global control styles

`input`, `select`, `textarea` and `.field` move into `app.css`, exactly as
`.btn` already lives there. `.field` is already a convention — defined
independently in five files — so this promotes an existing pattern rather than
inventing one.

Most of the fifteen duplicated blocks style bare `input, select` selectors, so
a global rule replaces them with no markup change at all.

## 0.5 Primitive components

**`Field` only.** The other two were measured and do not earn a component:

- `.card` is global, used 68 times, and redefined locally in **zero** files.
- `.btn` is global, with every state defined, and overridden locally in one
  file — a form-height rule added by 1.6, which 0.4 deletes.

A component wrapping either would add indirection and deduplicate nothing, and
both are already the single definition a primitive is meant to create.

The labelled-control shape is different: it appears about twenty-nine times and
`.field` was defined independently in five stylesheets. That is a primitive
worth having, and `Field` is it. The control is passed as a child rather than
as props, so every existing input, select and custom control keeps working
without being taught a new API.

**Building primitives at all was decided against my recommendation, and the
reasoning is recorded so the trade stays visible.** My advice was to take 0.3
and 0.4 — which capture the whole drift fix and delete the duplicated CSS with
no markup churn — and defer components until after Part 6, when it would be
known which markup shapes recur. The counter-argument, which is sound, is that
primitives cut code and ceremony at every call site, and doing it after
Parts 3-7 means migrating markup those parts have just written.

The cost accepted: roughly twenty-nine markup sites change. The mitigation:
Part 0 lands first, so Parts 3-7 are written against `Field` and migrate
nothing.

## 0.6 Enforcement

An ESLint rule, `design/no-raw-geometry`, modelled on the existing
`licence/header` rule in `eslint.config.js` — the precedent for a convention
that is enforced rather than remembered. It scans the `<style>` block of every
`.svelte` file under `src/`. `app.css` is exempt by definition: it is where the
tokens are declared.

**It covers `border-radius` and `gap`, and deliberately not `padding`.**

Padding was measured and cannot be scaled without restyling the product: 51
distinct two-value pairs, whose horizontal component is dominated by _odd_
numbers — `11px` in 27 places, `14px` in 20, plus 13, 15, 9, 7. Forcing them
onto an even scale is 50+ visible changes.

Padding drift is real, but it is a _duplication_ problem rather than a _scale_
problem: `8px 11px` is copied fifteen times and has already drifted to
`9px 11px` in one file. The fix for that is structural — the control padding
moves into the global control style and the `Field` primitive (0.4 and 0.5), so
it exists in one place and cannot drift. Decorative padding on a card or a
banner is a judgement, and a lint rule has no useful opinion about it.

The escape hatch is explicit and greppable:

```
/* geometry-exempt: donut diameter */
.donut { width: 148px; }
```

**If exemptions of a drift shape — a control, a card, a form row — exceed about
fifteen, the scale is wrong and this section is what should change.** One-offs
of a different kind, such as a pill or a circle, do not count against that
budget. This threshold is what caught the draft scale in 0.3 before any code
was written; it is meant to be used again.

**Tests.** Unit tests over the lint rule: a raw value fails, a token passes, an
exempted line passes, an exemption with no reason fails, and a value inside
`app.css` is never examined. The existing E2E viewport suite is the regression
net for the migration itself — fourteen screens at three widths, which is what
makes a sweep of this size safe to attempt at all.

# Part 1 — Confirmed bugs

Ten items, each with a diagnosed cause, none touching the schema. That is what
makes this part shippable on its own and first: it can land, be tried against
real data, and be judged before any migration exists.

## 1.1 Every retirement autosave has always failed

**Observed:** changing "the flats, once you retire" reports
`Could not save assumptions: The save writer is invalid.`

**Root cause.** `retirement/+page.server.ts:176` issues the autosave writer id
with `uuidv7()`. `WRITER_ID` at `settings/index.ts:94` is

```
/^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i
```

The version nibble is constrained to `[1-5]`. A UUIDv7's is `7`, so
`isRevisionWriterId()` rejects every id the page can possibly send. This is
not an edge case — no retirement assumption has ever saved through this path.

It escaped the suite because `tests/unit/retirement-save.test.ts:7` hand-writes
`99999999-9999-4999-8999-999999999999`, a v4-shaped literal that the app never
produces.

**Fix.** The regex is asserting a UUID _version_, and the writer id has no
reason to care which version it is — it is an opaque per-tab identity. Widen it
to any well-formed UUID, and keep the shape check so junk is still refused.
Note that `asRowId()` already maps a non-UUID to the nil UUID, which the
widened pattern must still reject: nil is "no such row", never a writer.

**Tests.** A unit test asserting `isRevisionWriterId(uuidv7())` is true, that
the nil UUID is false, and that junk is false. The existing save test switches
from its literal to a real `uuidv7()`, which is what would have caught this.

## 1.2 "Kept" is green when it is a loss

**Observed:** the Kept tile on Cash flow shows a negative figure in green.

**Root cause.** `FlowCard.svelte:27` hardcodes `style="color: var(--green)"`.

**Fix.** Colour by sign: `--green` at or above zero, `--red` below. "In" stays
green unconditionally — money in is not a signed quantity in that tile. The
Sankey itself already omits a non-positive `kept` node (`flow-graph.ts`,
`input.kept > 0`), so only the tile lies.

**Tests.** A component test over a negative, zero and positive `kept`.

## 1.3 The repeat-password box falls onto its own row

**Observed:** on Set up your household, "Repeat password" wraps below the row
it belongs to.

**Root cause.** `.person-row` (`setup/+page.svelte:66`) declares three grid
columns and the fieldset contains four inputs.

**Fix.** Four columns, and `.wrap` widens from 560px to 640px so four fields
fit without any of them becoming unusable. Below 640px the row becomes two
lines by design — name and birth year, then the two password boxes side by
side — rather than four stacked boxes.

**Tests.** The existing viewport suite gains the setup screen at the widths it
already covers, asserting the two password inputs share a row above 640px and
share a row with each other below it.

## 1.4 The bottom axis label lands on the year row

**Observed:** on _The pot against what the target requires_, the `0.0` label
overlaps the `2026` year label, and the horizontal lines do not line up with the
figures beside them.

**Root cause.** Not what it looks like. The labels _are_ centred on their
position — `.axis` already carries `transform: translateY(-50%)`
(`retirement/+page.svelte:761`). The fault is what the percentage is measured
against.

`chart.axis` places labels at `top: 0% / 50% / 100%`, absolutely positioned
against `.chart`. On this screen `.chart` contains the `<svg>` **and the
`.years` row** — `height: 16px; margin-top: 4px` — so its height is the plot
plus 20px. Every label is therefore displaced downward in proportion to how far
down it sits, and the 100% one lands squarely on the year row.

The investments chart draws the identical pattern and is correct, which is the
proof: there `.years` is a _sibling_ of `.chart`, not a child, so 100% is the
bottom of the plot.

**Fix.** Move the `.years` div out of `.chart` on the retirement screen, so
`.chart` contains only the axis labels and the plot they annotate — matching
investments exactly. Nothing else changes: the existing `translateY(-50%)` then
centres each label on its gridline, and `0.0` sits on the baseline where it
belongs.

This is deliberately the smaller of the two available fixes. Adding a bottom
inset to `.chart` would also move the label off the year row, but would leave
the 50% label off its gridline — a subtler wrong that would survive the fix.

**Tests.** A viewport test asserting the bottom axis label's box does not
intersect the first year label's box, at the widths already covered. That
assertion fails today.

## 1.5 Map this layout: the columns do not line up

**Observed:** on the mapping wizard the header, the role select and the sample
text are at different heights across columns.

**Root cause.** `.w-columns` is an `auto-fit` grid and each `.w-col` is its
own independent grid (`import/+page.svelte:528-537`). A two-line header in one
column pushes that column's select down; its neighbours' do not move.

**Fix.** `.w-col` becomes `grid-row: span 3; grid-template-rows: subgrid`, so
all three bands share the parent's rows and align across every column.

**Tests.** A viewport test over a preview whose headers differ in height,
asserting the selects share a `y` position.

## 1.6 The payslip field is wider than its neighbours

**Observed:** in _Salary history_, the payslip file input is larger than the
other fields in the row.

**Root cause.** A file input's intrinsic width is set by its button and the
filename text, and `.payslip-form` gives it no track of its own.

**Fix.** Constrain the file input to the same track as its siblings and let the
filename ellipsize. This is the same class of fault the 390px file-input
overflow fix addressed earlier in v0.3.11 and uses the same approach.

## 1.7 The add form reopens itself

**Observed:** after adding a property, the wizard for the next one is already
open. The same on Loans.

**Root cause.** `addingProperty` / the loan equivalent are never cleared on a
successful submit, so the form the enhance callback re-renders is the open one.

**Fix.** Close on success in the `use:enhance` result handler; leave it open on
a failure so what was typed is still there to correct.

**Tests.** E2E: add a property, assert the form is gone; submit an invalid one,
assert it remains with its values.

## 1.8 The trailing dot on the actual line

**Observed:** _Value against money in_ draws a green dot at the right-hand end
of the line, which reads as a defect rather than as data.

**Fix.** Drop the `<circle>` markers (`investments/+page.svelte:175`). The line
carries the series; the note beneath it already says market value is taken at
report dates.

## 1.9 "Other" is not where it belongs in the bank list

**Observed:** in the account form's bank select, _Other_ sits wherever the
alphabet puts it.

**Root cause.** `accounts/+page.server.ts:35` orders by `bank.label`.

**Fix.** Order by label, then move _Other_ to the end of the data list. The
`➕ Add a bank…` sentinel stays last of all, below it — it is not a bank.

**Tests.** A unit test over the ordering helper.

## 1.10 Two type sizes for the same thing

**Observed:** filenames in the import queue and filenames under _Recent
imports_ are different sizes.

**Root cause.** A leftover from the 22→9 type-token collapse earlier in this
release; the two lists were converted to different tokens.

**Fix.** One token for both.

# Part 2 — Reachable at every address

## 2.1 What actually happens

**Observed:** opening the app on a phone over the LAN, typing the password,
and getting `Cross-site POST form submissions are forbidden` — offered as a
file to download rather than shown as a page.

**Root cause.** SvelteKit compares the browser's `Origin` header against
`url.origin` in `respond.js:82`, and adapter-node takes `url.origin` from the
`ORIGIN` environment variable (`handler.js:101`, `base: origin ||
get_origin(req.headers)`). `ORIGIN` names one address. Browsing any other —
the LAN IP, `continuum.local`, the tailnet name — mismatches, and every form
POST on the instance is refused, sign-in first.

The download is a second-order effect: the refusal is a `text/plain` body
(`respond.js:99`), which Safari saves rather than displays.

The check runs before `handle`, so no hook can improve it.

## 2.2 `ORIGIN` is doing two unrelated jobs

Separating them is the whole of this part.

1. **It pins `url.origin`,** which is what the CSRF check compares against.
2. **It is the passkey relying party.** `webauthn/origin.ts:41`
   `currentOrigin()` reads `env.ORIGIN`; `relyingPartyId()` is its hostname;
   `passkeysUsableFrom()` compares the browsed origin to it.

Unsetting `ORIGIN` to fix (1) would silently make `currentOrigin()` return `''`
and every passkey report itself `unconfigured`. So the two roles are split
rather than one being sacrificed.

## 2.3 The change

**`url.origin` becomes request-derived.** A thin Node entry point wraps
adapter-node's handler and, before importing it, sets

```
PROTOCOL_HEADER=x-forwarded-proto
HOST_HEADER=x-forwarded-host
```

and defaults `x-forwarded-proto` to `http` when the header is absent.

That default is the load-bearing detail. adapter-node's own `get_origin()`
falls back to `'https'` when no protocol header is set
(`handler.js:210`), which is wrong for a plain-HTTP LAN address and would leave
the mismatch in place while looking fixed. The app itself always speaks HTTP;
`https` reaches it only through a proxy, and every proxy in the supported
set — the Tailscale sidecar included — sends `x-forwarded-proto`.

**CSRF protection is not weakened.** The check becomes "the origin the browser
reports must match the host it addressed", which is the property that matters.
A cross-site POST from `evil.com` sends `Origin: https://evil.com` against
`Host: continuum.local` and is still refused. What is given up is protection
against a forged `Host` header, which for a LAN or tailnet deployment is not
the threat the setting was defending against.

**`ORIGIN` survives, narrowed to one job.** Set, it still pins `url.origin`
exactly as today, so no existing deployment changes under its owner. Its
documented meaning becomes _the single HTTPS address passkeys are bound to_:

- unset → password sign-in from every address, no passkey controls anywhere;
- set → passkeys additionally work at that one address.

`passkeysUsableFrom()` already implements precisely this and needs no change.

**The residual refusal gets a page.** The wrapper detects the 403 CSRF body
and substitutes an HTML page naming the address the browser used, the address
the server expects, and what to do about it — instead of a file called
`login.txt`.

## 2.4 Documentation

`ORIGIN` appears in `README.md`, `docs/install.md`, `docs/networking.md`,
`SECURITY.md`, `compose.yaml`, `.env.example` and `docker/DOCKERHUB.md`, all
describing it as the address form submissions are checked against. Every one
is rewritten to the new meaning, and `compose.yaml`'s default
`ORIGIN: ${ORIGIN:-http://localhost}` is removed so a fresh instance is
reachable at whatever address its owner uses.

**Tests.** Unit tests over the wrapper's header defaulting: absent
`x-forwarded-proto` becomes `http`; a proxy-supplied `https` is preserved; a
set `ORIGIN` still wins. E2E: sign in over a `Host` that is not `localhost`.

# Part 3 — Import and the category tree

Eleven items. Eight are here; the catch-all ordering is 3.8, and the three with
no design content are noted at the end and implemented in Part 1.

## 3.1 The Revolut export cannot prove itself

**Observed:** a real Revolut CSV falls through to _Map this layout_ and cannot
be imported.

**Root cause, proven.** Revolut exports every _pocket_ into one file, keyed by
the `Product` column. The reporter's file holds 1798 `Current` rows and three
`Savings` rows, and the Savings pocket has its own balance chain
(`0.17 → 0.00 → 0.00`) and its own dates (June 2024, appended after August
2026 rows). `parseRevolut` builds a single statement from all of it, so:

- `periodStart`/`periodEnd` read `2024-06-19 → 2024-06-20`;
- `closingBalanceMinor` reads `0`, taken from a "Closing transaction" row in a
  pocket that is not the account being imported;
- the running-balance check fails, and `assertAgreesWithItsOwnNumbers` throws.

Measured directly against the proof engine:

| Input                                   | Proof class | Running balance   |
| --------------------------------------- | ----------- | ----------------- |
| file as exported                        | **P0**      | fails             |
| same file, three `Savings` rows removed | **P3**      | passes, 1798 rows |

Two things this is _not_. Fees are handled correctly — `proof.ts:67` nets
`amountMinor - feeMinor`, and all 31 fee-bearing rows chain. `REVERTED` rows
are already skipped by the `State` filter and correctly carry no balance.

**Fix.** Group rows by `Product` and emit one `ParsedStatement` per pocket.
`adapterOrGeneric` already accepts an array, so the plumbing exists. Each
pocket gets its own currency, period and closing balance, and proves itself
independently. A pocket whose rows are all filtered out contributes nothing.

**Tests.** A fixture derived from the reporter's export — reduced and with
counterparties anonymised — asserting two statements, the Current one proving
P3 across all its rows, and the Savings one proving on its own three. Plus a
regression test that the single-pocket sample still parses unchanged.

## 3.2 The Fio movement list can never prove itself

**Observed:** `Pohyby_na_uctu-….csv` offers _Map this layout_, and mapping it
by hand still does not import it.

**Root cause.** This export is a movement list, not a statement. Its columns
are `Datum;Objem;Měna;Protiúčet;Kód banky;Zpráva pro příjemce;Poznámka;Typ` —
no balance, no opening or closing figure, no totals. Nothing in it can answer
whether every row is present, so it is P0, and `decideImport` refuses P0 even
for a confirmed mapping. That refusal is correct and stays.

The missing counterparty numbers on the interest and interest-tax rows are
unrelated. The same rows appear in the reporter's `Výpis z účtu` export for the
same account and import without trouble.

**Fix.** Recognise this header and refuse it by name, instead of offering a
mapping screen where no answer can succeed:

> This is Fio's "Pohyby na účtu" export. It lists movements but prints no
> balances, so nothing in it can show whether every row is there. In
> Internetbanking choose "Výpis z účtu" instead — same account, and it prints
> the opening and closing balances.

The signature must be specific enough not to claim ordinary Czech CSVs, in the
spirit of the `#Numer rachunku` lesson recorded in `detect.ts:140`: the full
ordered header, not a substring of it.

**Tests.** The reporter's file (anonymised) asserting the named refusal; the
`Výpis z účtu` sample for the same account asserting it still imports.

## 3.3 Statements are never filed

**Observed:** imported statements should be kept in Documents, tagged, on
their own shelf.

**What already exists.** `import_file.storedName` keeps the original bytes on
the data volume (`ingest.ts:723`), deliberately, so parser improvements can
re-parse history. The file is retained today; it is simply not surfaced.

**Fix.** A new `document.shelf` value `statements` — nine exist and none fits.
On a successful import, a `document` row is created pointing at the
`storedName` the importer already wrote. No second copy of the bytes.

- **Title** from what the statement proved about itself:
  `Fio · 2101106516 · July 2026`, falling back to the filename when no period
  could be read.
- **Linked** to the account, through the same `documentLink` mechanism used
  elsewhere, so it also appears on that account.
- **Tagged** with the bank, the account and the year.

**Only accepted statements are filed.** A refusal produced no ledger rows, so
filing it would put unreadable files on the shelf with nothing to say about
them.

**Schema.** A migration widens `document_shelf_check` to include `statements`.
Widening a CHECK constraint accepts more than it did and rejects nothing it
previously allowed, so it is additive under the v0.3.9 lock.

**Tests.** Integration: import a statement, assert a `statements`-shelf
document exists, points at the same `storedName`, links to the account and
carries the three tags. Assert a refused import files nothing.

## 3.4 The queue never clears

**Observed:** finished queue entries stay; there is no way to cancel one or to
dismiss it.

**Fix.** An ✕ on every queue row.

- `queued` → **cancel**: the job is removed and its blob released.
- `done` / `failed` → **dismiss**: the row leaves the view.
- `running` → **disabled**, with a hint saying it is being read now. A read
  under way cannot be stopped honestly, and pretending otherwise would leave a
  half-ingested statement.

A finished row also disappears on its own **ten minutes after `finishedAt`**,
which the `job` table already records. No new column, and no timer — the query
filters on it.

**Tests.** Integration over each state's ✕ behaviour; a unit test over the
ten-minute filter boundary.

## 3.5 Recent imports never clear

**Fix.** An ✕ that acknowledges a recent import and hides it. This one needs
state: an additive `import_file.acknowledged_at` timestamp, null by default.

Dismissing hides a row. It does not delete the `import_file` record, the
transactions it produced, the stored statement, or the document from 3.3. The
content hash that makes a re-upload a no-op is untouched, so acknowledging an
import cannot cause it to be imported twice.

**Tests.** Integration: acknowledge, assert hidden; assert the record,
transactions and document survive; assert re-uploading the same file is still
recognised as a duplicate.

## 3.6 Deleting a category always demands a destination

**Observed:** pressing ✕ on a category always opens a "move what is filed under
this to…" form, even when nothing is filed under it — and it opens inline,
pushing the rest of the list down.

**Root cause.** `settings/+page.svelte:645` marks `reassignTo` as `required`
and renders the form unconditionally, and `deleteCategory(id, reassignTo)`
(`taxonomy.ts:196`) takes the destination as a mandatory argument. Nothing ever
counts what depends on the category first, so an unused one costs the same
three decisions as a heavily used one.

**Fix, in two parts.**

_Count before asking._ Before rendering anything, count what points at the
category:

- money — `transaction.category_id`, `transaction.suggested_category_id` and
  `transaction_split.category_id`;
- rules — `rule.category_id`.

If every count is zero, the ✕ deletes it outright. There is no question to ask,
so none is asked.

_Ask in a dialog, not in the list._ When something does depend on it, the
question goes in a modal — the existing `Modal.svelte`, as the split, repay,
refix and tax-statement dialogs already use — rather than expanding inline. It
names the counts rather than implying them:

> **Delete "Groceries"?**
> 412 transactions and 3 rules are filed under it.
> ○ Move them all to [ Everything else ▾ ]
> ○ Leave them and I will reassign them myself
> [ Cancel ] [ Delete ]

Rules are named separately from money because they behave differently: a rule
left pointing at a deleted category still matches and files nothing, so the
categoriser quietly stops working. That is why `deleteCategory` already
repoints them, and why the dialog says how many are affected.

"Leave them and I will reassign them myself" abandons the delete and filters
the register to that category, which is the screen where the reassignment is
actually done. It does **not** delete the category and orphan the rows — the
integrity rule stands: nothing is deleted while anything points at it.

**Tests.** Integration: a category with no dependants deletes with no
destination and no dialog; one with dependants refuses a destination-free
delete; the move path repoints transactions, suggestions, splits and rules in
one transaction; choosing the category being deleted as the destination is
refused. E2E: the dialog appears only in the second case.

## 3.7 The category picker opens into nothing

**Observed:** opening _Choose a category…_ near the bottom of the screen
expands downward off-screen; nothing is visible until the page is scrolled.

**Root cause.** It is a native `<select>` with `<optgroup>`s
(`import/+page.svelte:357`). Popup placement is decided by the browser and
cannot be steered by the page.

**Fix.** A listbox component that:

- **flips** above or below the trigger by measured available space;
- **scrolls** inside whatever room it has, never extending past the viewport;
- keeps the group headings, keyboard navigation, typeahead and the ARIA
  combobox roles a native select provides for free.

This is the largest single item in the release, and it is worth it because it
is not one screen: the same control is on Transactions
(`transactions/+page.svelte:190`), and both move to it.

**Tests.** Unit tests over the placement decision at the boundaries — room
below, room above, room in neither, which pins to the viewport and scrolls.
Accessibility tests for roles, keyboard traversal and typeahead. Viewport tests
opening the picker from the last row on the shortest supported screen.

## 3.8 Category order is not yours, and catch-alls drift up the list

**Observed:** _Other income_ sits fifth in Income, above _Interest_, because
_Interest_ was added later and took the next free sort value. More generally
there is no way to say what order categories should be in.

**Root cause.** `CATEGORY_SEED` gives `other-income` sort 4; a category added
afterwards takes 5. Nothing pins a catch-all, and nothing lets a household
express an order at all.

**Fix — both mechanisms, with a stated rule for which wins.**

_Drag to reorder._ The category chips inside a group become draggable in
Settings. Dropping one writes new `sort` values for that group in a single
transaction, and that order is the order everywhere the categories are
listed — the pickers, the filters, the breakdown strip.

_A pinned catch-all._ An additive boolean `category.is_catch_all`, default
false, seeded true for `everything-else` and `other-income`. A flagged category
is always last within its group and is not draggable.

_The rule between them:_ ordering is `is_catch_all, sort, name`. The flag wins
over `sort` always, so no drag can put a category below the catch-all and no
newly added category can land beneath it. Dragging governs the order of
everything above the line; the flag governs the line itself.

The flag is deliberately not a name match. A household that renames _Everything
else_ to _Odds and ends_ keeps the behaviour, which a name match would silently
lose. Whether a category is a catch-all is editable in Settings — it is a
property of how the household thinks, not a fact about the seed data.

**Tests.** Unit tests over the comparator: a flagged category sorts last
whatever its `sort`; two flagged categories in one group fall back to `sort`
then `name`; an unflagged category added after the catch-all still sorts above
it. Integration: a drag persists and survives a reload; a drag cannot move a
chip below a flagged one. E2E: reorder in Settings, then assert the new order
on the import screen's picker.

# Part 4 — Accounts and loans, editable

Five reported items across four sections: the bank ordering is implemented as
1.9, with the rest below.

## 4.1 An account cannot be corrected

**Observed:** a mistyped account cannot be changed — not its name, not its
bank, not its type.

**Fix.** An edit form on each account row: name, emoji, bank, kind, account
numbers, owner. It reuses the add form's controls, including the bank select
with its _Other_-then-_Add a bank_ ordering from 1.9.

**Currency is not editable once the account holds transactions.** Every stored
amount is minor units of the account's currency and the account is the
authority for what an imported statement is denominated in. Changing it later
would reinterpret history. It stays editable while the account is empty and is
refused after, with a sentence saying why rather than a disabled control saying
nothing.

**Tests.** Integration over each field; a test asserting the currency refusal
once a transaction exists and the currency edit succeeding while none does.

## 4.2 Every account is joint by omission

**Observed:** an added account is automatically joint, with no way to say whose
it is.

**Root cause.** `addAccount` never sets `ownerPersonId`, and the row meta falls
back to the string `'joint'` when the join finds no person
(`accounts/+page.server.ts:60`).

**Fix.** An owner select — _Joint_, or a named member of the household — on
both the add and the edit form. _Joint_ remains the default, and remains a real
answer rather than an absence.

**Tests.** Integration: add with each choice; edit between them.

## 4.3 Account numbers are invisible

**Observed:** the account numbers a statement is matched against are never
shown.

**Root cause.** `account.numbers` is written at creation _and_ extended by the
importer when a statement teaches an account a number it did not have
(`ingest.ts:367`) — but the column is selected nowhere and rendered nowhere.
The information that explains why transfer pairing did or did not fire is
unreachable.

**Fix.** A second line under the account name listing the numbers it is known
by, mono, in `--fg3`:

```
🏦  Fio joint account
    2101106516/2010 · CZ65 2010 0000 0021 0110 6516
    CZK · joint · statement to 2026-07-31          239,79 CZK
```

The numbers become editable in the edit form from 4.1, so one learned from a
misfiled statement can be corrected rather than living on invisibly. An account
with none shows no second line; the existing `ⓘ` hint on the add form already
explains what they are for.

**Tests.** Integration: numbers render; a number learned by an import appears;
editing removes one.

## 4.4 A loan cannot be fully edited

**Observed:** rate regime, interest changes and interest accrual are fixed
after creation.

**Root cause.** `updateLoan` (`loans/mutations.ts:324`) accepts name, lender,
kind, paymentDay, endsOn and secured. Nothing else.

**Fix.** Extend it with rate regime, accrual style, interest deductibility, and
the ability to record an interest-rate change.

**The existing guard is preserved.** `updateLoan` refuses an end date that
falls inside recorded history, because truncating fixation periods to fit would
be a deletion. Every field added here is held to the same rule: an edit that
would invalidate or remove a recorded period is refused with a sentence, never
silently applied. Changing accrual style re-derives the schedule forward; it
does not rewrite periods already recorded.

**Tests.** Integration per field, plus a test for each refusal: an edit that
would strand a fixation period is rejected and the periods survive intact.

# Part 5 — Property and investments

Six items.

## 5.1 A property's value is a single number with no history

**Observed:** changes in external valuation should be tracked so they can be
plotted.

**Fix.** A new table:

```
property_valuation
  id           uuid pk
  property_id  uuid  → property.id  on delete cascade
  valued_on    date
  value_minor  bigint
  currency     text  → currency.code
  source       text          -- purchase | estimate | appraisal | index
  note         text
```

`property.value_minor` and `valued_on` stay as they are and become a
denormalised view of the latest row, written whenever a valuation is added, so
every existing reader keeps working unchanged. Past valuations can be entered
for a flat owned for years, and the series plots.

## 5.2 Adding a property you have owned for years is hard

**Observed:** money-in is difficult to establish for a property that predates
the ledger.

**Fix.** An opening position, recorded once rather than reconstructed:

```
property_opening
  property_id      uuid pk → property.id  on delete cascade
  purchased_on     date
  price_minor      bigint
  costs_minor      bigint       -- fees, tax, legal
  deposit_minor    bigint
  currency         text → currency.code
```

`property.money_in_minor` is computed from it — deposit plus costs plus
principal repaid, the last already derivable from the loan — and remains
directly editable for a household that would rather type one number. Recording
the purchase also seeds a `property_valuation` row with `source: purchase`, so
the value series starts where the ownership did.

**Tests.** Integration: adding an opening position produces the expected
money-in and the seed valuation; editing money-in directly still works.

## 5.3 What you own is drawn too small for its box

**Observed:** the donut does not use the space the card gives it.

**Root cause.** `.donut-wrap` stacks vertically and `.donut` is a fixed 148px
(`investments/+page.svelte:365-378`).

**Fix.** Donut left, legend right, the donut sized from the box rather than
fixed, stacking back to a column below the width where two columns stop
working. The Accounts donut is left alone — its card is a different shape and
it is not what was reported.

## 5.4 Tax on realised gains

**Observed:** an estimate of the tax owed this year on realised gains, shown
beside portfolio value and money in, with the rate configurable.

**Fix.** A tile showing realised gains year to date, the rate, and the product.

- **The rate is configurable**, stored as a setting. No jurisdiction is
  assumed and no rate is hardcoded.
- **A holding-period exemption is optional and off by default.** When switched
  on, disposals of positions held longer than a configurable number of years —
  defaulting to three — are excluded from the taxable figure. This matches the
  Czech time test, which is why it is offered, and why it is a switch rather
  than a rule: it is specific to one jurisdiction.

The tile says _estimate_ on its face. It is arithmetic over what the broker
reports, not tax advice, and it does not know about losses carried forward,
other income, or anything outside this instance.

**Tests.** Unit tests over the calculation: rate only; rate with the exemption
on and disposals either side of the threshold; zero and negative realised
figures.

## 5.5 Years are not marked on Value against money in

**Fix.** A vertical rule at each year boundary, drawn at the weight the
existing gridlines use so it reads as structure rather than as data. The year
labels already exist beneath the plot and stay.

Implemented in 1.8.

# Part 6 — Navigation and the Sankey

Five reported items across four sections: 6.1 answers both the Documents tab
and the Settings gear.

## 6.1 Documents and Settings do not belong together

**Observed:** Documents should be its own tab after Calendar; Settings should
be a gear beside the wordmark.

**Fix.** In `modules/registry.ts`, the `admin` area is removed. `documents`
becomes its own area, placed after `calendar`. Settings leaves the sidebar
navigation entirely and becomes a gear button in the sidebar's brand row, to
the right of the wordmark.

`/settings` keeps its path, so every existing link to it — including the
"Close it" link from 6.3 and the install hint at `Sidebar.svelte:140` —
continues to work. `areaForPath()` must keep resolving `/settings`, which no
longer belongs to any area; the active-state logic needs to tolerate that
rather than assume every path has one.

**Tests.** Unit tests over `visibleAreas()` and `areaForPath()` for
`/settings` and `/documents`. E2E: the gear reaches Settings; Documents is its
own row after Calendar; switching the documents module off removes the row and
leaves the gear.

## 6.2 The open-instance banner is everywhere

**Observed:** with password protection off, _"This instance is open — anyone
who can reach it can sign in as anyone"_ appears on every screen. It should
appear in Settings, for an administrator.

**Root cause.** `(app)/+layout.svelte:119` renders it on every page,
deliberately — the comment argues open mode is invisible from inside once you
are in.

**Fix.** The banner leaves the layout. Settings keeps its own, fuller notice
(`settings/+page.svelte:698`), shown to an administrator.

This is a real trade, and it is the reporter's call: someone who did not turn
it on will not be told the instance is open unless they visit Settings. The
sign-in page keeps its notice (`login/+page.svelte:49`), which is where a
person who did not expect it will actually meet it — before they are inside.

**Tests.** E2E: with open mode on, no banner on Overview; the notice present in
Settings for an admin and absent for a non-admin; the sign-in notice unchanged.

## 6.3 Setup cannot turn password protection off

**Observed:** the wizard should be able to create a household with no password.

**Fix.** A checkbox on Set up your household: _no password — anyone who can
reach this can sign in as anyone_. Checked, the password fields are disabled
and the `openMode` setting is written true as the household is created.

Two rules from `auth/open-mode.ts` are honoured rather than routed around.
Turning it on later requires an administrator to re-enter their password,
because that is the last moment a password can prove intent — at setup there is
no password yet and no instance to protect, so the checkbox itself is the
intent. And passwords are never deleted: a household created open can be closed
later, at which point every person sets one through the normal path.

**Tests.** Integration: setup with the box checked creates the household with
`openMode` true and no password hashes; unchecked behaves exactly as today.
E2E: sign in without a credential afterwards.

## 6.4 The Sankey says too much and crosses itself

**Observed, three faults.** Labels are drawn at every node and overflow the
card; ribbons cross; a legend duplicates what the labels say.

**Root cause of the crossings.** `sankey.ts:180` claims "Two median sweeps then
reduce crossings" and does not do them — there is one forward pass ordering
each column by mean parent position. And the ribbon comment claims bands
"arrive stacked in source order", but `sortedLinks` sorts by target `y`, so the
in-cursor accumulates in target order at both ends.

**Fix, in three parts.**

_Labels._ Totals in and out are always drawn. Every other label is drawn only
when its band has room for it — measured against the node's height, not
assumed — and is otherwise omitted.

This is what the reporter saw as "text shows all and is not scaled".
`relaxLabels()` always spaces labels by `LABEL_H`, so they do not overlap each
other; when a column carries more labels than the box has room for, the clamp
at `sankey.ts:137` pins the block to the top and the tail runs off the bottom
of the card. Spacing is not the problem — quantity is. So the omission decision
happens before relaxation, on how many labels there is room for at all.

_Hover._ Hovering a node or a ribbon shows its name and figure. The diagram
gains pointer targets, which it does not have today (`pointer-events: none` on
labels, nothing on the geometry).

_The breakdown strip stays._ It is the only place leaf categories are readable
on a phone, where there is no hover at all. Removing it would trade one
legibility problem for a worse one.

_Crossings._ Add the backward median sweep the file already claims, and stack
ribbons at the target in source order rather than target order. Both are
deterministic; the existing invariant tests — nothing outside the box, ribbons
flush with their nodes, columns conserving their total — must still pass, and
gain one more: a crossing count that does not regress across the synthetic
graph sweep.

**Tests.** Unit tests over the label-omission decision at a range of node
heights; a crossing-count assertion over the existing synthetic sweep;
accessibility tests for the hover content's keyboard equivalent.

# Part 7 — Salary history from the ledger

Lands last: it needs Part 3's category picker and Part 4's account ownership.

## 7.1 Salary history cannot see the bank

**Observed:** salary history is typed in or read from an uploaded payslip. A
salary already sitting in the ledger — categorised as such by the person who
imported the statement — is invisible to it.

**Root cause.** There is no salary table. Salary history is assembled entirely
from `document` rows on the `payslips` shelf carrying an `amountMinor` and a
`document_link` to a person (`retirement/+page.server.ts:116-144`). A bank
figure has nowhere to live, and an edit to one has nowhere to persist.

## 7.2 Gross and net are two fields, not two rows

A payslip states **gross**. A bank credit is **net**. They are not competing
readings of the same number and neither should win — an observation carries
both:

```
salary_entry
  id            uuid pk
  person_id     uuid  → person
  period_month  text        -- YYYY-MM
  gross_minor   bigint null -- from the payslip
  net_minor     bigint null -- from the bank credit
  currency      text  → currency.code
  source        text        -- payslip | statement | manual
  document_id   uuid  → document     null
  transaction_id uuid → transaction  null
  amount_overridden boolean          -- the figure was corrected by hand
```

A payslip and a bank credit for the same person and month merge into one row,
each filling its own column. A derived row stays editable and can gain a
payslip later, which is what makes the bank a starting point rather than a
verdict.

**The yearly figures do not mix the two.** `salaryStats()` already reports how
many months each year it saw; it gains a second series, so a year shows an
average gross over the months that have one and an average net over the months
that have one, each with its own month count. A year with payslips for four
months and bank credits for twelve says exactly that, rather than silently
averaging four gross figures with eight net ones and calling it a salary.

## 7.3 Whose salary it is

Attribution runs: transaction → account → `account.owner_person_id`.

**This is why the part lands after Part 4.** `addAccount` never sets an owner
today, so every account is joint by omission and every payment would take the
path below.

For an account with an owner, the salary is theirs and nothing is asked.

For a joint account, the question is asked **in the category picker**, as a
sub-selection that appears when a category needing attribution is chosen:

```
Category  [ Salary            ▾ ]
Whose?    [ Robert            ▾ ]   ← appears only for Salary, joint account
          [x] remember for “ACME Corp”
```

This extends the picker Part 3 builds, which is the second reason this part is
last.

The memory is a small dedicated table:

```
salary_attribution
  id            uuid pk
  match_key     text      -- normalised counterparty, e.g. the employer
  person_id     uuid → person
  account_id    uuid → account  null
```

**Deliberately not the `rule` table.** That engine's payload is `category_id`:
it maps a transaction to a category. Adding a person to it would let the
categoriser start assigning people, mixing two jobs that fail differently — a
miscategorised coffee is a nuisance, a salary attributed to the wrong person
corrupts two retirement projections.

**Tests.** Unit tests over the merge: payslip only, bank only, both, and both
with the amount overridden. Integration: a salary transaction on an owned
account creates an attributed entry; on a joint account it creates an
unattributed one; answering once attributes every later payment from the same
counterparty. Unit tests over the two-series yearly figures, including a year
with gross for some months and net for others.
