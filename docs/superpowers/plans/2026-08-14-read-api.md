# Read-only JSON API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose the ledger core and its summary figures as a read-only JSON API under `/api/v1`, authenticated by bearer tokens managed in Settings.

**Architecture:** Every endpoint calls the same server functions the screens call, so the API and the UI cannot disagree. Tokens are stored as a sha256 hash exactly as sessions already are. Money crosses the wire as integer minor units plus a currency code, never a float.

**Tech Stack:** SvelteKit (Svelte 5 runes), TypeScript strict, PostgreSQL via Drizzle ORM, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-14-read-api-design.md`

## Global Constraints

- **Robert makes all git commits.** Never run `git commit`. Each task ends with a verification checkpoint; stop there and report.
- Money is integer minor units (`bigint`) plus a currency code. Never floats, never pre-formatted strings.
- Nothing variable is hard-coded.
- Server-only code lives under `src/lib/server/`. Pure logic lives elsewhere under `src/lib/`.
- The API is read-only. No endpoint in this plan creates, updates or deletes anything except an API token.
- Tests: `npm test`, `npm run test:e2e` (needs `npm run build` and the database), `npm run check`, `npm run lint`.
- E2E is one ordered serial journey; new tests append to existing state.

### Task 1: Serialisation

Pure, and first, because the money rule is the part with the longest tail.

**Files:**

- Create: `src/lib/api/serialise.ts`, `tests/unit/api-serialise.test.ts`

**Interfaces:**

- Produces:

  ```ts
  interface Money {
  	amountMinor: number;
  	currency: string;
  }
  function money(amountMinor: bigint, currency: string): Money;
  ```

  There is no generic deep-converter. Each endpoint calls `money()` explicitly at
  the field it applies to, so a `bigint` that nobody thought about becomes a
  `JSON.stringify` error at development time rather than being silently coerced
  by a helper that guesses.

```ts
// How money crosses the wire: an integer of minor units and a currency code.
//
// Never a float — that would lose the precision the whole ledger is built to
// protect — and never a pre-formatted string, which would force consumers to
// parse language-specific separators back out.

export interface Money {
	amountMinor: number;
	currency: string;
}

export function money(amountMinor: bigint, currency: string): Money {
	// bigint does not survive JSON.stringify, so it has to become a Number. At
	// household scale this range cannot be exceeded; the guard exists so that if
	// it ever is, it fails loudly instead of quietly reporting a wrong figure.
	if (
		amountMinor > BigInt(Number.MAX_SAFE_INTEGER) ||
		amountMinor < BigInt(-Number.MAX_SAFE_INTEGER)
	)
		throw new Error(`Amount ${amountMinor} is outside the safe integer range for JSON`);
	return { amountMinor: Number(amountMinor), currency };
}
```

Expected: 4 passed.

```ts
import { createHash, randomBytes } from 'node:crypto';
import { desc, eq } from 'drizzle-orm';
import { db } from '$lib/server/db';
import { apiToken } from '$lib/server/db/schema';

/** Same hashing as sessions: the raw token never touches the database. */
export function hashToken(raw: string): string {
	return createHash('sha256').update(raw).digest('hex');
}

export async function createToken(label: string): Promise<{ raw: string }> {
	const raw = randomBytes(32).toString('base64url');
	await db.insert(apiToken).values({ id: hashToken(raw), label: label.trim() || 'Unnamed token' });
	return { raw };
}

/** True when the token is known. Stamps lastUsedAt so dormant tokens show up. */
export async function verifyToken(raw: string | null): Promise<boolean> {
	if (!raw) return false;
	const id = hashToken(raw);
	const rows = await db.select().from(apiToken).where(eq(apiToken.id, id));
	if (!rows[0]) return false;
	await db.update(apiToken).set({ lastUsedAt: new Date() }).where(eq(apiToken.id, id));
	return true;
}

export async function listTokens() {
	return db.select().from(apiToken).orderBy(desc(apiToken.createdAt));
}

export async function revokeToken(id: string): Promise<void> {
	await db.delete(apiToken).where(eq(apiToken.id, id));
}
```

### Task 3: The guard and the first endpoint — the checkpoint

If authentication works and an unauthenticated request is refused, everything after this is shape.

**Files:**

- Modify: `src/hooks.server.ts`
- Create: `src/lib/server/api/respond.ts`, `src/routes/api/v1/accounts/+server.ts`

**Interfaces:**

- Produces: `requireToken(request): Promise<Response | null>` — a `401` response, or null when authorised.

- [ ] **Step 1: Exempt /api from the session redirect**

In `src/hooks.server.ts`, add `/api` to `PUBLIC_PATHS` with a comment matching the existing one:

```ts
// /ics/<token> is public by design: calendar apps subscribe without a session,
// authenticated by the secret token in the URL. /api authenticates itself the
// same way, with a bearer token instead of a cookie.
const PUBLIC_PATHS = ['/login', '/setup', '/ics', '/api'];
```

This exempts `/api` from the _redirect to login_, not from authentication — each endpoint calls `requireToken` itself. A route that forgets to is a bug, which is why Task 6's E2E checks an unauthenticated request is refused.

- [ ] **Step 2: Write the responder**

Create `src/lib/server/api/respond.ts`:

```ts
import { verifyToken } from '$lib/server/api/tokens';
import { loginBlockedForSeconds, recordLoginFailure } from '$lib/server/auth/ratelimit';

export function json(body: unknown, status = 200): Response {
	return new Response(JSON.stringify(body), {
		status,
		headers: { 'content-type': 'application/json; charset=utf-8', 'cache-control': 'no-store' }
	});
}

export function apiError(message: string, status: number): Response {
	return json({ error: message }, status);
}

/**
 * Null when the caller is authorised, otherwise the response to return.
 * Failed attempts are rate limited with the same limiter the login screen uses:
 * an endpoint that lets a caller try tokens without limit is a guessing oracle.
 */
export async function requireToken(request: Request, address: string): Promise<Response | null> {
	const wait = loginBlockedForSeconds(address);
	if (wait > 0) return apiError('Too many failed attempts.', 429);

	const header = request.headers.get('authorization') ?? '';
	const raw = header.startsWith('Bearer ') ? header.slice(7).trim() : null;
	if (await verifyToken(raw)) return null;

	recordLoginFailure(address);
	return apiError('Unauthorised.', 401);
}
```

Note `recordLoginSuccess` is deliberately **not** called on a valid token: it would clear the failure counter for that address, letting an attacker reset their budget by interleaving one known-good request. Successful API calls simply do not touch the limiter.

- [ ] **Step 3: The first endpoint**

Create `src/routes/api/v1/accounts/+server.ts`:

```ts
import { db } from '$lib/server/db';
import { account } from '$lib/server/db/schema';
import { json, requireToken } from '$lib/server/api/respond';
import { money } from '$lib/api/serialise';
import type { RequestHandler } from './$types';

export const GET: RequestHandler = async ({ request, getClientAddress }) => {
	const refused = await requireToken(request, getClientAddress());
	if (refused) return refused;

	const rows = await db.select().from(account).orderBy(account.createdAt);
	return json({
		accounts: rows.map((a) => ({
			id: a.id,
			name: a.name,
			bank: a.bank,
			kind: a.kind,
			balance: money(a.balanceMinor, a.currency),
			balanceAsOf: a.balanceAsOf
		}))
	});
};
```

## Notes for the implementer

**Task 3 is the checkpoint.** If an unauthenticated request returns a `303` redirect rather than a `401`, the `PUBLIC_PATHS` change did not take effect and every endpoint after it is unprotected in a way tests might not notice.

**Never call `recordLoginSuccess` from the API.** It clears the failure counter for that address, which would let a caller reset their guessing budget by interleaving one valid request.

**Every amount goes through `money()`.** Not `Number(x)`, not `x.toString()`. The guard against silent rounding only helps if nothing bypasses it.

**Endpoints reuse the screens' server functions.** `parseFilter`, `registerPage`, `tagTotals`, the net-worth composition. A second query written for the API is a second thing to keep in step, and it will drift.
