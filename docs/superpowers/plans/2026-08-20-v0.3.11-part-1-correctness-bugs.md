# v0.3.11 Part 1 — Correctness Bugs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the nine defects observed in the first real session of use, so the XTB import works, the money screens show data that exists, and controls tell the user what they did.

**Architecture:** Nine independent tasks against an existing SvelteKit 2 / Svelte 5 application with a Drizzle-managed Postgres schema. Server logic lives under `src/lib/server/<module>/`, screens under `src/routes/(app)/<screen>/`. Pure functions get unit tests under `tests/unit/`; anything that depends on a real database constraint gets an integration test under `tests/integration/` using the embedded-Postgres harness. No task depends on another; they may be done in any order, though Task 1 unblocks a workflow in daily use and should go first.

**Tech Stack:** SvelteKit 2, Svelte 5 (runes mode, enforced), TypeScript, Drizzle ORM, postgres.js, Vitest, Playwright, Prettier, ESLint.

**Spec:** `docs/superpowers/specs/2026-08-20-v0.3.11-design.md` — Part 1 in full, plus the schema rule in Part 8.

## Global Constraints

- **Never create a git commit.** Robert makes every commit himself. Where this plan's tasks end, they end with verification, not `git commit`. Do not run `git commit`, `git add -A`, or `git push` under any circumstances. Leave changes in the working tree and report what changed.
- **The schema is additive-only** (v0.3.9 lock). No table is dropped, no column is dropped, no column changes type. Task 9 in particular removes a _user interface_, not the `loan.interest_deductible` column.
- **Every new file starts with** `// SPDX-License-Identifier: PolyForm-Noncommercial-1.0.0` as its first line.
- **Svelte components are runes-mode.** Use `$state`, `$derived`, `$props`, `$effect`. `export let` and `$:` are compile errors in this project.
- **Money is `bigint` minor units** with a currency code beside it. Never `number`, never floats. Convert with the helpers in `$lib/money`.
- **Derive, do not hardcode.** Constants are acceptable only for format facts and arithmetic. A threshold that encodes a presentation judgement gets a named constant with the reasoning in a comment beside it.
- **Verification commands**, all run from the repository root:
  - `npm run test:unit` — Vitest, includes `tests/unit/`, `tests/integration/`, `tests/acceptance/`
  - `npm run check` — svelte-check against `tsconfig.json`
  - `npm run lint` — ESLint plus `prettier --check`
  - `npm run format` — Prettier write, to fix lint formatting failures
- **A task is not done until `npm run lint` and `npm run check` both pass**, not only its own test.

### Task 1: XTB import survives operations that reference positions

**Why this is first:** this blocks a workflow in use today. Every XTB report containing a dividend, a withholding tax or a closed position fails to import.

**Files:**

- Modify: `src/lib/server/invest/ingest.ts` — export `ingestReport`; reorder the position and operation loops; guard `positionId`
- Test: `tests/integration/broker-ingest.test.ts` _(create)_

**Interfaces:**

- Consumes: `BrokerReport`, `BrokerCashOperation`, `BrokerPositionSpan` from `src/lib/server/invest/adapter.ts` (already exported)
- Produces: `export async function ingestReport(report: BrokerReport, handle: Db): Promise<Omit<BrokerIngestResult, 'broker'>>` — currently module-private at `ingest.ts:39`. Exporting it is the seam the test needs; building a synthetic `.xlsx` to reach the same code would test the parser instead of the bug.

**Background you need.** `broker_operation.position_id` is a real foreign key to `broker_position.id`, declared at `src/lib/server/db/schema/investments.ts:37`. It is not deferrable. `ingestReport` currently writes every operation (loop at `ingest.ts:108`) before any position (loop at `ingest.ts:130`), inside one transaction. The first operation naming a position that is not already in the table aborts the whole transaction.

Reordering is necessary but not sufficient. A report can name a position it does not contain — a correction filed in July against a position opened and closed in a window the user never uploaded. Those operations must still be stored, with `positionId` null.

```typescript
			.from(schema.brokerOperation)
```

- [ ] **Step 4: Guard the position link**

Immediately after the moved position block and before the operations loop, add:

```typescript
// An operation may name a position this report does not carry — a correction
// filed against a position opened and closed in a window that was never
// uploaded. The cash movement is still real, so it is stored with a null link
// rather than aborting the whole report. The set is read AFTER the positions
// above are written, so a position supplied by this very report resolves.
const storedPositions = new Set(
	(await tx.select({ id: brokerPosition.id }).from(brokerPosition)).map((row) => row.id)
);
const linkFor = (positionId: string | null) =>
	positionId && storedPositions.has(positionId) ? positionId : null;
```

Then in the operations loop, replace both occurrences of `op.positionId`:

```typescript
			.values({
				id: op.id,
				type: op.type,

				amountMinor: op.amountMinor,
				currency: accountCurrency,
				comment: op.comment,
				positionId: linkFor(op.positionId)

			.onConflictDoUpdate({
				target: brokerOperation.id,
				set: { positionId: linkFor(op.positionId) }
			});
```

### Task 3: Reproduce the Accounts hang — investigation only

**This task deliberately produces no fix.** The spec records it as the one item with no diagnosed cause, and a speculative change to a page whose failure nobody has observed in a debugger is how a real bug gets hidden behind a plausible edit.

**Files:**

**Interfaces:**

- Produces: a reproduction record. If the cause is found, a follow-up task is written against it; the fix is not attempted inside this task.

**Background.** Reported as: after importing a statement containing transactions, clicking Accounts in the sidebar does nothing — no navigation, no error page, no visible change. The absence of an error page rules out a throwing `load`, because SvelteKit renders its error boundary for those. The `load` at `src/routes/(app)/accounts/+page.server.ts:25` does four things that only become reachable once transactions exist: per-account FX conversion through `loadRateTable()`, a donut over cash accounts, a `transfer_pair` query, and a join fetching both legs of every pair.

- [ ] **Step 1: Get a populated instance running**

Start the app against a database with at least one account and one imported statement containing transactions. Use a real statement from `bank_data_examples_do_not_share/` — the bug was reported against real data, and synthetic rows may not carry whatever shape triggers it.

- [ ] **Step 2: Reproduce with instrumentation open**

With the browser devtools open on the Console and Network tabs, and the server log visible, click Accounts in the sidebar. Capture all three at the moment of the click:

- Console: any unhandled rejection or error
- Network: whether a request for the navigation is issued at all, and if so whether it completes, hangs, or returns non-200
- Server log: whether `load` is entered, and whether it returns

- [ ] **Step 3: Narrow it**

Depending on what Step 2 shows:

- **No network request at all** → the client router never started. The fault is in the sidebar link or a navigation guard, not in `load`. Inspect `src/lib/components/Sidebar.svelte`.

```typescript
/**
 * The window a period covers, anchored on the newest month that actually holds
 * data rather than on the calendar.
 *
 * Statements arrive after a month ends, so "this month" is routinely empty and
 * the screens rendered nothing at all. Anchoring on the data means a household
 * mid-way through importing sees July and is told it is looking at July.
 *
 * `anchorMonth` is null only on an instance with no transactions, where falling
 * back to today keeps the empty state exactly as it was.
 */
export function periodRange(
	period: Period,
	anchorMonth: string | null,
	today = new Date()
): { start: string; end: string; caption: string } {
	const anchor = anchorMonth
		? new Date(Date.UTC(Number(anchorMonth.slice(0, 4)), Number(anchorMonth.slice(5, 7)) - 1, 1))
		: today;
	const y = anchor.getUTCFullYear();
	const m = anchor.getUTCMonth();
	const end = new Date(Date.UTC(y, m + 1, 0)).toISOString().slice(0, 10);
	const monthName = (index: number) =>
		new Date(Date.UTC(2000, index, 1)).toLocaleString('en', { month: 'long' });

	if (period === 'month') {
		return {
			start: new Date(Date.UTC(y, m, 1)).toISOString().slice(0, 10),
			end,
			caption: `${monthName(m)} ${y}`
		};
	}
	return { start: `${y}-01-01`, end, caption: `January – ${monthName(m)} ${y}` };
}
```

Note the switch from `getFullYear`/`getMonth` to their UTC counterparts. The old code mixed local-time reads with `Date.UTC` writes, which lands on the wrong month for anyone west of UTC during the first hours of a month.

```typescript
/**
 * The newest month holding a transaction that is not a transfer leg, as
 * `YYYY-MM`, or null on an instance with nothing imported.
 *
 * The two rules here are not free choices — they are the rules monthlyHistory
 * and flowData already apply. The effective date is the value date when the
 * bank prints one, and transfer legs are excluded. A month whose only movement
 * was between the household's own accounts has no spending to show, and
 * anchoring on it would reproduce the empty chart this exists to fix.
 */
export async function latestMonthWithData(): Promise<string | null> {
	const [row] = await db
		.select({
			month: sql<
				string | null
			>`to_char(max(coalesce(${transaction.valueOn}, ${transaction.bookedOn})), 'YYYY-MM')`
		})
		.from(transaction)
		.where(isNull(transaction.transferPairId));
	return row?.month ?? null;
}
```

```typescript
// SPDX-License-Identifier: PolyForm-Noncommercial-1.0.0

/**
 * Two years. Below this the axis labels months, above it years.
 *
 * A presentation judgement rather than a derived fact, so it is named and
 * explained rather than inlined: at two years a per-month axis is around 24
 * labels, which is the point where they stop being readable at the width this
 * chart is given. A household three months into importing was previously shown
 * a single year label under every bar, which told them nothing at all.
 */
const YEARLY_TICKS_FROM_MONTHS = 24;

export function historyTicks(months: string[]): { unit: 'month' | 'year'; labels: string[] } {
	if (months.length >= YEARLY_TICKS_FROM_MONTHS) {
		return { unit: 'year', labels: [...new Set(months.map((m) => m.slice(0, 4)))] };
	}
	return { unit: 'month', labels: months.map((m) => m.slice(5, 7)) };
}
```
