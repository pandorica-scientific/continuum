# v0.3.8 — UI to build

The interface work implied by the ingest changes. Read `docs/ui-guidelines.md` first for
_how_ to build; this is _what_. Behaviour and rationale live in
`docs/v0.3.8-implementation-plan.md`.

---

## The organising idea

Every statement now arrives with a **proof class** — how strongly it proved itself — and
that maps onto the traffic-light pill exactly, which is what the pill exists for:

| Proof | Pill | Meaning to the user |
|---|---|---|
| P4 · P3 | 🟢 `green` | Balances check out. Filed, nothing to do. |
| P2 · P1 | 🟡 `yellow` | Totals agree but not every row is individually proven. |
| P0 | 🔴 `red` | Nothing could be proven. Needs a person. |

Never show the user the string "P4". Show the pill and a plain phrase — *"balances check
out"*, *"totals agree"*, *"couldn't verify"* — with the detail on demand. The proof class is
our vocabulary, not theirs.

**Voice.** The existing import copy sets it: *"Statements in, transactions filed. Only the
ambiguous ones ask for you."* Terse, confident, faintly wry. Never apologetic, never chirpy.
Errors say what happened and what to do.

## 1. Import screen, restructured

`src/routes/(app)/import/+page.svelte`

One file can now yield **several statements** (a CAMT file with three accounts, a workbook
with a sheet each). The result list is therefore **per statement, not per file** — today it
is keyed on `filename`, which will collide.

```
scan_2026_07.pdf
  ├ Fio CZK ·2010    🟢  41 added · 3 known · 2 paired
  └ Fio EUR ·2010    🟡  6 added · 0 known          totals agree
wyciag_07.csv        🔴  couldn't verify — needs a look   [ Review ]
```

Each row: source file, account, proof pill, counts, and an action only when one is needed.
Group by file when a file produced more than one statement; a single-statement file renders
one flat row with no grouping chrome.

Keep `UploadDropzone`. Fix its `accept` — it currently advertises `.xml,.ofx,.abo`, which
the parser rejects. After this release those are genuinely supported, plus `.xlsx`, `.png`,
`.jpg`.

## 2. Upload queue with progress

**New.** The rule is absolute: **nothing blocks the interface.** Deterministic parsing is
instant and returns inline; anything needing rasterisation is queued and the upload returns
immediately.

```
Reading 2 of 5                                    [ 3 waiting ]
  scan_2026_07.pdf     reading page 3 of 12   ▓▓▓▓▓░░░░░░░
  wyciag_07.pdf        queued
```

- Show **queue depth** as well as per-file progress — the user needs to know five files are
  waiting, not just that one is moving.
- Per-file states: `queued` → `reading` (with page x of y when OCR is running) → resolved
  row → or `failed` with a reason.
- Progress must survive a page refresh; it is server state, not component state.
- A finished item becomes an ordinary result row in place. Do not clear the queue on
  completion — the user wants to see what happened.
- Build the bar as a primitive (`ProgressBar.svelte`): 1px `--bd` track, `--brand` fill, no
  shadow, no stripes, no animation beyond the fill width. Respect
  `prefers-reduced-motion`.

## 3. The single-question resolver

**New, and the most important screen in the release.** When everything about a file resolved
except one thing, ask about **that one thing only**. The full wizard is for files we cannot
read at all.

```
One thing is unclear about this file

  Dates could be day-first or month-first,
  and nothing in the file settles it.

  ( ) day-first     03.07 → 3 July      11.07 → 11 July
  ( ) month-first   03.07 → 7 March     11.07 → 7 November

  Everything else was verified against the statement's own balances.

                                    [ Import ]  [ Show full mapping ]
```

- Render the competing readings as **real rows from their file**, never as abstract format
  strings. `DD/MM` means nothing; *"3 July or 7 March"* is a decision anyone can make.
- State plainly what was already proven — it earns the trust that makes the one question
  feel small.
- Always offer an escape hatch to the full mapping, for the user who wants to check.
- Reuse `Modal`. Options are radios, not a `Segmented` — these are consequential and
  deserve labels with examples, not compact chips.

**Do not** make this generic-looking. Resist a reusable "resolve ambiguity" component that
renders any dimension the same way. Each dimension (date order, decimal mark, sign
convention, which column is the amount) deserves its own concrete rendering, because the
whole point is that the user sees their own data, not a form.

## 4. Full mapping wizard

**New.** For a file matching no profile. Steps, all on one screen — this is a table with
controls above it, not a multi-page flow:

1. Detected: delimiter, encoding, header row, region. Shown as read-only facts with an
   "adjust" affordance, not as inputs demanding attention.
2. Column mapping: each detected column gets a role picker (date · value date · amount ·
   debit · credit · balance · counterparty · account · reference · description · ignore).
   Pre-filled from the header dictionary and the arithmetic.
3. Live preview: five parsed rows rendered exactly as they will appear in the ledger, with
   the running balance check shown passing or failing as the user edits.
4. Save as a named profile.

The preview is the whole design. A mapping is abstract; five rows of their own money are
not.

## 5. Format drift

**New.** A saved profile stops matching because the bank changed its export.

> **This export changed since last time.**
> Two new columns appeared. Your previous mapping is filled in below — check the
> highlighted ones and we'll remember the new layout.

Pre-fill the old mapping, highlight only what moved, and **never present this as an error**.
The user did nothing wrong; their bank changed. Old files keep parsing under the old profile
version.

---

## 6. Arbitration review

**New, PDF only.** Neither the text layer nor the OCR read reconciled. Show both reads side
by side with the disagreeing rows marked, and let the user pick a source — not individual
cells. We never splice a row that exists in neither read.

Include the page image alongside, cropped to the disputed rows. The user is arbitrating a
document; give them the document.

## 7. Statement detail — the evidence

**New.** Opened from a result row. This is where the proof class becomes legible:

```
Fio CZK ·2010 — July 2026            🟢 balances check out

  ✓ running balance chain closes on all 41 rows
  ✓ opening 382,38 + credits 62 652 − debits 50 050 = closing 12 984,38
  ✓ credit and debit totals match the statement
  — row count not printed by this bank

  read by      text layer (Fio CSV profile v2)
  source       Vypis_z_uctu-2500834780…csv
```

Checks as a plain list with pass/fail/not-applicable marks. "Not printed by this bank" is a
neutral dash, not a failure — most of the checklist being unavailable is normal and must not
read as alarming.

## 8. Transaction provenance

Extend the existing transaction detail. Day to day the ledger looks unchanged; provenance
appears on demand:

```
read by      OCR (tesseract, ces)
verified     balance chain ✓ 47/47 rows
source       scan_2026_07.pdf · page 2 · lines 14–16
profile      ČS PDF v1
```

Plus filters on the import screen: `all` · `from OCR` · `unverified`. A `Segmented` fits
here.

## 9. Profile manager

**New**, in Settings. List of saved profiles: name, bank, format, verified badge, last used.
Actions: rename, edit mapping, export as JSON, import a JSON profile, delete. Built-in
profiles are listed but read-only, visually distinct from the user's own.

Export/import is what lets a mapping made once be contributed back — make it a visible
button, not a hidden menu item.

---

## 10. Not a bank statement

**New.** A document with balances but no movements is a holdings snapshot, not a statement.

> **This looks like a portfolio statement.**
> It lists what you hold, not money moving in and out, so there is nothing to file into the
> ledger.
> [ Send to Investments ]  [ Keep as a document ]

Two real actions. Never a bare rejection — the file is legitimate, it just belongs
somewhere else.

---

## 11. Scan quality warning

**New.** Shown *before* the wait, not after the failure, when an uploaded image falls below
the measured resolution floor.

> This scan is 110 dpi. Statements usually need about 300 dpi to read reliably — this one
> will probably need checking by hand. Continue anyway?

Advisory, never blocking. Measure the real floor after the word-geometry extractor lands
and put the true number here.

## Reuse, don't rebuild

| Need | Use |
|---|---|
| Proof state | `Pill` with `hue` from `$lib/ui/hue.ts` |
| Any dialog | `Modal` |
| Filters | `Segmented` |
| Counts on the import screen | `MetricTile` |
| Section headers | `Eyebrow`, `ScreenHeader` |
| Errors | `ActionError` |
| Explaining a mechanism | `InfoHint` |
| File input | `UploadDropzone` |

**Genuinely new primitives:** `ProgressBar` only. Everything else composes.
